agentic-memory and agentic-tools size every text they embed so it fits the embedder's input limit, measured once per endpoint, and gain an `embedding_path` option for OpenAI-compatible gateways, matching sdd's embedding sizing decision so one embedder behaves the same in both tools.

Why: an embedder past its input limit discards the tail without an error and answers a vector of the head. rapid-mlx at 127.0.0.1:1235 cuts at 2048 tokens and logged a 33,356-token input. Prompt recall embeds the user's whole prompt uncapped, as does a `search --query` phrase; an entry chunk is 3200 runes plus an uncapped `Entry: <title>` prefix, which dense code or CJK text takes past 2048 tokens; a tool's text (summary, usage, inputs, outputs) is uncapped. And the OpenAI adapter appends `/v1/embeddings` to any endpoint not ending in `/v1`, so a gateway such as Opper (`/v3/compat/embeddings`) answers 404.

**Sizing.**
- Where the provider reports a token count (OpenAI `usage.prompt_tokens`, Ollama `prompt_eval_count`), sizing follows it. Without a count, every input is capped at 2048 runes, title prefix included.
- Calibration runs once per endpoint with three single-input probes: about 1000 runes of Latin text (tokens per rune), about 1000 runes of CJK (the worst ratio), and about 20000 runes (the limit: the plateau of the reported count where truncation is silent, or a bisection between the last accepted size and the first error where the provider refuses). The result is stored keyed by the vector fingerprint plus the endpoint URL and path, and recalibrated when either changes; a changed endpoint re-embeds nothing.
- The chunk size is the limit divided by the worst tokens per rune, with a margin. Counts reported by later batches refine the ratio; a batch whose count says an input was cut is split until that input is isolated and re-chunked.
- Queries (a recall prompt, a `search --query` or `find --query` phrase) are cut to the chunk size before they are embedded; entry chunks and tool texts are chunked to it.
- No hook waits on calibration beyond its existing deadline: until an endpoint is calibrated, the 2048-rune cap applies.

**Path.** `embedding_path`, default `/v1/embeddings`, names the OpenAI-compatible route appended to `embedding_endpoint`; a gateway sets its own. Like the endpoint it is read only from Claude Code's settings, and under the sdd fallback it is taken from sdd's `path` key in the same allowed layers as sdd's endpoint. Ollama keeps `/api/embed`.

**Fingerprint.** The vector fingerprint stays provider, model, dimensions and the template hash: vectors depend on those, not on the route or the server, so no store re-embeds on this change.

**Rejected.**
- A fixed rune cap alone: it either wastes context on large-limit models or still overflows small ones on dense scripts.
- A limit option per provider: the owner set no config key for limits; the probes measure what an option would make each user look up.
- Detecting the route from the endpoint's suffix: sdd chose an explicit `path` key, and the two tools must resolve the same provider the same way.
- Putting the path into the vector fingerprint: it would re-embed every store for no change in vectors.

**Accepted costs.** Three probe requests per endpoint, once; a stored calibration per endpoint in the cache; queries longer than the chunk size are embedded by their head; one more option in `plugin.json`, the README and both embedding docs.

**Done when** a prompt or text over the limit is cut or chunked before it reaches the embedder (tests with a fake embedder enforcing a token limit and reporting counts); calibration stores and reuses its result per endpoint and re-probes on change; a provider without counts gets the 2048-rune cap; `embedding_path` reaches the request URL, from own options and from the sdd fallback; the fingerprint is unchanged; every new guard is broken and seen failing; a live run against rapid-mlx shows no truncation line for a 33k-token prompt.
