The first release with the agent-neutral home of d-tac-6xf moves every project's old data into it in one machine-wide migration, run automatically by its first call, while sessions still running an older release are fenced off rather than left writing to trees nobody reads any more.

**Trigger and lock.** Any call of the new release (every hook, `agentic-memory`, `agentic-tools`, `agentic-capture`, `agentic-helpers`, and the `memory` and `tools` MCP servers) that finds an old tree and no `<data>/format.json` runs the migration. It holds a machine-wide lock exclusively; every other call of the new release takes the same lock shared, so it waits for the migration and never reads a half-moved home. Apart from that one wait, the lock costs a call nothing measurable.

**What moves.** Each old project key (an sdd `repo_id`, or `local/` plus a hash of the git common dir) under `~/.claude/agentic-memory`, `~/.claude/agentic-tools` and `~/.claude/agentic-helpers` becomes one store, memory and tools of one key joined:
- a key whose `writers.json` names a checkout that still exists becomes an ordinary store under `stores/`, its `identity.json` holding the legacy key, every listed checkout, the volume UUID plus inode of each, and the `agentic-store` pointer written into each checkout's git common dir;
- a key whose checkout lies on a volume that is not mounted becomes an ordinary store identified by path, its pointer written at the first visit;
- every other key becomes an unclaimed store under `<data>/unclaimed/`, stamped with the migration time.
Seat registries (`seats.json`, `shelves.json`), seat files and the stores' own `backup/` folders move with their store; the session tree `~/.claude/agentic-memory/sessions` moves to `<data>/sessions/claude/`; the machine-wide attachments folder moves to `<data>/attachments/`. Data moves by rename where source and target share a volume, and by copy, check and remove where they do not. The small metadata files (`writers.json`, `seats.json`, `shelves.json`, every `format.json`) are copied to `<data>/backup/legacy-<UTC stamp>/` first; bulk data is not copied, since a failed run renames it back.

**Completion.** `<data>/format.json` is written last: its presence marks the migration done. A failure before it renames every moved tree back, removes every pointer written, reports `agentic-helpers: migrating to <data> failed: <cause>; nothing moved, and the next call tries again` once per session, and leaves the old layout working, as the store migration of d-tac-jyw does.

**Fencing.** Sessions started before the update keep running the older release, since a running session keeps the plugin version it started with. They are kept from writing into trees nobody reads any more:
- each old memory store folder is left as a stub holding only a `format.json` with a format no released version reads, so the older release's hooks stay silent and its CLI and MCP tools refuse with its own line, `agentic-memory: this store has format <n>; this release reads up to <m>`;
- `~/.claude/agentic-tools` and `~/.claude/agentic-helpers` are replaced by a file naming the new home, so the older release finds no library to read and refuses every write, and its writers check admits no checkout.
Cache trees (`~/.cache/agentic-*`) are not fenced: they hold only what can be rebuilt, and shell-guard's countdown state in them keeps an older session's guard working as before. The new release removes them, and the fence files and stubs, in one sweep once the process table shows no `agentic-*` process of an older release, whichever projects have or have not been opened since. An idle MCP server of the new release runs the sweep silently under the exclusive lock; where none runs, a hook starts it detached at session end, so no call waits for it.

The migration asks the user nothing; questions, if any, come later from the mapping of d-tac-6xf and only for the checkout a session runs in. Releases before 2.3.0 met the same restart cost (s-tac-5fz).

**Rejected.** A migration per project at that project's first call: old trees and new stores would coexist indefinitely, and an older session could keep writing to a project already moved. An explicit `agentic-helpers migrate`: every component refuses until someone runs it. Leaving older sessions unfenced: their writes would land in trees the new release never reads, and be lost without a word. Fencing the caches too: an older session's shell-guard would lose its countdown state for nothing a rebuildable cache could cost. A full copy as backup: doubles the space of every store and the attachments for a run whose failure path already restores by rename.

**Accepted costs.** Sessions started before the update have no memory or tool library until they restart; nothing they filed earlier is lost. The first call after the update waits for the whole migration. An older release's refusal line for a fenced tools library says only that the path is no directory.

**Acceptance.**
- A functional test builds an old home in `t.TempDir()` from fixtures (memory and tools stores under `repo_id` and `local/` keys, `writers.json` with existing, unmounted and vanished checkouts, sessions, attachments) and finds after one call: ordinary, offline and unclaimed stores as above, pointers in every existing checkout's git common dir, `<data>/format.json` last, metadata backups, stubs and fence files in place.
- A write fault injected before `<data>/format.json` leaves the old home byte-identical, writes no pointer, prints the failure line once, and the next call migrates.
- Two calls starting on one unmigrated home migrate it once, the second waiting on the lock; run under `-race`.
- The released binary of the previous version, run against a migrated home, prints nothing at every hook and refuses every memory and tools write without writing anything.
- No question is asked during the migration.
- Cache trees and fences are gone once no older-release process runs, and never while one does.
