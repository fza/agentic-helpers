Agentic-memory attachments and the agentic-tools library each get one machine-wide size limit, 2 GB for attachments and 500 MB for tools, alongside their per-item caps, with tool versions pruned oldest first to make room, space computed from sizes recorded at write time, and the cap and space left shown to the agent before it writes.

Why: the attachment budget of d-tac-15x counts per project while the attachment store is one per machine, and the tool library of d-tac-e9x has no limit beyond its per-tool cap, so every stored version stays forever. The agent-neutral home (d-tac-6xf) left size limits to a decision of their own; this is it.

**Attachments.**
- `attachments_total_mb` (default 2048) limits every attachment across every project on the machine, counting each stored file once. It retires the per-project `attachment_budget_mb` (500 MB). Over it, the attach is refused naming the size, with the entries and seats holding the most bytes, as the budget refusal of d-tac-15x does.
- `attachment_max_mb` (10 MB) per file stays.
- Attachments are never pruned automatically: a file ends only with its entry's body, as d-tac-15x sets.

**Tools.**
- The per-tool cap stays 1 MiB (`docs/tools/architecture.md`), now stated to the agent before a tool or version is registered; `add` and `update` refuse above it.
- `tools_total_mb` (default 500) limits every tool library across every project on the machine. Every stored version counts on disk.
- The library makes room by itself where it can: it removes prunable versions, oldest first. A version is prunable when it is not its tool's current version and no fork names it as its origin. Every removed version's file hashes stay in the index, so the duplicate check of d-tac-e9x still refuses a byte-identical re-add.
- Pruning runs in the SessionStart pass that already visits every store for purges, and inside a write that needs room. A write is refused only when nothing prunable is left.

**Where the keys live**, per the config layering of d-tac-cld: `attachments_total_mb` and `attachment_max_mb` only refuse a write, so they stay overridable. `tools_total_mb` decides when stored versions are deleted, so it lives in `config.yaml` only.

**Invariant.** An overall limit set below its per-item limit is silently raised to that per-item limit.

**Space shown.** Space shown to the agent leaves prunable versions out: used is the bytes of non-prunable versions, left is the limit minus that.

**The agent knows before writing.**
- The caps (`attachment_max_mb`, the 1 MiB per-tool cap) appear in the `agentic-helpers:agent-memory` and `agentic-helpers:agent-tools` skills, in the `attach`, `new`, `add` and `update` MCP tool descriptions, and in `--help`.
- Space left appears in one memory-brief line, printed at claim, resume and compaction: `space left: attachments <left> of <limit>, tools <left> of <limit>`.
- Every `attach`, `add` and `update` reply ends with the same figure for its own store kind.

**Listing.** The memory view language gains the filter word `attached` (entries holding attachments) and the rank key `size` (an entry's total attachment bytes). Its list shows each file's name and size and the total, for example `agentic-memory view 'active:attached:rank(size):as-list'`.

**Accounting.** Space used and left is computed from metadata the stores record at write time, never by walking directories: each attachment's size from the memory log's `attach` row, each tool version's file sizes from the tool index. A write adds its size to the recorded total; a purge, a prune or a retirement subtracts it. A `du` or stat walk over the stores is far too slow for a figure printed in the brief and in every write reply.

**Rejected.**
- An attachment limit of 1 GB or 500 MB: too tight for build logs and screenshots across every project on the machine.
- A per-tool cap of 5 MB: a helper tool is a script, and 1 MiB already holds any reasonable one.
- Refusing at the tools limit with no pruning: the library fills with unused history and then refuses new tools.
- Counting only current tool versions: the disk grows past the limit without bound.
- A PreToolUse hook per write announcing space left, or a read command for it: one costs a hook message on every write, the other a call the agent must think to make.
- A directory walk for space: too slow per call.

**Accepted costs.**
- An old tool version a session took can vanish from the store; its copy in the checkout's `.tmp/tools/` stays.
- The brief's space figure ages over a long session; the write replies carry a fresh one.
- Recorded totals can drift from the disk after a crash between a write and its record, until the next purge pass recomputes them from the log and index.

**Acceptance.**
1. An attach over `attachments_total_mb`, counted across two fixture projects sharing one file once, is refused with the size and the largest holders; `attachment_budget_mb` is no longer read or declared.
2. An `add` or `update` over 1 MiB is refused.
3. With the tools library at its limit, a write prunes the oldest prunable version first, never a current version or a fork's origin, and is refused only when nothing prunable is left.
4. A pruned version's files still refuse a byte-identical `add` as a duplicate.
5. `tools_total_mb` set as an agent option has no effect; set in `config.yaml`, it does. `attachments_total_mb` set as an agent option overrides `config.yaml`.
6. An overall limit below its per-item limit resolves to the per-item limit.
7. The brief prints the `space left:` line with prunable versions left out; every `attach`, `add` and `update` reply carries its figure.
8. `view 'active:attached:rank(size):as-list'` lists attached entries by size with each file's size and the total.
9. Space figures match a fixture's recorded sizes, and a test asserts no directory walk runs to compute them.
10. Skills, MCP descriptions, `--help`, README `Options` and `docs/` name every key, cap and line above, in the same change.
