agentic-memory keeps entry vectors in immutable, memory-mapped segment files in place of the whole-file `vectors.gob`, following sdd's search segments. It replaces the vector-cache mechanic of 20261025-021209-d-tac-1pj, which judged one whole-file rewrite cheaper than segments at a few thousand entries.

- **Layout.** `<cache>/<fp12>/segments/<sha256>.seg`: a header (magic, format, dims, row count, table length); a table of one row per entry, each the entry id, its content hash and its chunk count, lengths and counts as uvarints; zero padding to a 64-byte boundary; the vector block, one normalized little-endian float32 vector per chunk, an entry's chunks contiguous and in table order, so a row's vectors start at the sum of the chunk counts before it. No payloads: search needs only the id and the hash.
- **Liveness comes from the fold, with no manifest.** A row counts only where its entry is live and the row's hash equals the entry's current content hash. A re-embedded entry's old row goes dead by itself; copies with the same hash are interchangeable.
- **A write is one new segment.** A fill embeds what is missing and writes one segment through a unique temporary file, fsync and rename: O(rows written).
- **Tiered merge** under `segments.lock` after a write: only segments within a size ratio of 4 merge; a segment with no live row is unlinked; a segment is rewritten alone once its dead rows outnumber its live ones. Amortised cost per write O(k log N).
- **Lock-free reads over mmap.** A segment is mapped read-only and shared (`golang.org/x/sys/unix`, already a requirement), with `MADV_WILLNEED` for a cold scan; the search is an exact dot-product scan over the mapped block, an entry scoring by its best chunk, decoding and copying nothing. A file is only ever created by rename and removed by unlink, so a mapping outlives an unlink. The MCP server keeps its mappings across calls, keyed by segment name.
- **Migration.** On first open an existing `vectors.gob` becomes one segment and is removed, with no embedder call.

Why: filing an entry and searching both cost time proportional to the whole store, so every entry filed slows every later search and fill.

Rejected:

- Keeping `vectors.gob`: O(N) per write and per search.
- An append-only gob log: a search still decodes all of it.
- sdd's chromem layout of one file per row: opening it costs one file per row.
- A manifest or journal: the fold already says which rows are live.
- HNSW: approximate results, nothing to gain at this size.

Accepted costs: a process writing the cache can plant vectors that skew ranking, as it can with `vectors.gob` today (20261025-185324-s-tac-k4o), but a planted row never surfaces an entry the fold does not hold; Unix only, matching the release targets darwin and linux.

Done when tests cover a format round trip, a torn temporary file ignored, a stale-hash row ignored, the merge planner bounding the segment count for 2,000 entries filed one at a time, `vectors.gob` migrated with no embedder call, and a mapping surviving the unlink of its file, each guard broken and watched failing; `docs/memory/architecture.md` describes the layout.
