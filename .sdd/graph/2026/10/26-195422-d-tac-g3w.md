The hooks find a project's graph where sdd does, through one resolver in `internal/graphconfig`: walk up to the governing `.sdd/`; when its `config.yaml`, overlaid by `config.local.yaml`, sets `project_dir`, the graph project is the folder that path names, the one holding the graph repository's `.sdd/` (an absolute path kept as is, a relative one joined to the folder holding the code repository's `.sdd/`); otherwise it is the folder holding that `.sdd/`. Within the graph project, entries live under its own `graph_dir` (an absolute path kept as is, a relative one joined to the folder holding the graph project's `.sdd/`, `.sdd/graph` where unset). Both joins follow sdd's own rule, which resolves against the parent of `.sdd/` rather than the git toplevel.

Every reader of the project's sdd state moves to the resolved graph project:

- The grounding gate's `graphState()` (20261025-182429-d-tac-fhx), which counts entry files to tell when credited reads went stale, its ledger under `.sdd/tmp/`, and `.sdd/grounding.yaml`.
- agentic-memory's graph links (20261025-180343-d-tac-p9f): a graph id resolves against the entry file under the resolved path, and the status cache keys on the files there. Its entry language comes from the graph project's `language`.
- The project key (`repo_id`) that names the memory and tools store, so a code repository and its graph repository share one store.
- `agentic-capture`'s graph lookup and its lock.

A code repository's `graph_dir` pointing outside its own repository is not followed. sdd keeps a split layout's graph-side state (`graph_dir`, `repo_id`, `language`, `meta.json`, `tmp/`) in the graph repository and holds only `project_dir` in the code repository, and refuses a code-repository `graph_dir` reaching elsewhere.

Why: every reader walks `<root>/.sdd/` and `<root>/.sdd/graph` only. A code repository linked to a sibling graph repository (`gvb-mika`, graph in `gvb-mika-sdd`) holds an empty stray `.sdd/graph`, so `graphState()` stays `0:` for good: credit never goes stale, and entries other sessions capture never re-owe a read. A graph kept at `graph_dir: graph` (`format-d-devlab-sdd`) has no `.sdd/graph` at all, with the same blindness. Every memory `--link` to a graph id there refuses with `no such entry`, the memory language falls back to the plugin's, and the store key falls back to a path hash, splitting the code repository's memory from the graph repository's.

Rejected:

- Following a code-repository `graph_dir` that points into another repository as well: a second path living only until sdd refuses that configuration, removed again once it does.
- Asking `sdd config get`: a subprocess on every gate and record call, where two small YAML reads answer the same.
- Following `graph_dir` only when no `.sdd/graph` exists: a stray empty directory would still win.

Accepted costs:

- `gvb-mika` stays blind until it carries `project_dir`, which waits on sdd shipping it.
- The resolution copies sdd's rule; a change to how sdd reads `project_dir` or `graph_dir` has to be followed here.
- A `project_dir` or `graph_dir` naming a missing checkout counts as an empty graph, as a missing `.sdd/graph` does today.

Acceptance criteria:

1. In a code repository whose `.sdd/config.yaml` sets `project_dir` to a sibling graph repository, `graphState()` counts the entries under the graph repository's `graph_dir`, a new entry there voids credited reads, and the ledger and `grounding.yaml` are the graph repository's.
2. `project_dir` set only in the code repository's `config.local.yaml` is followed.
3. A graph repository with `graph_dir: graph` and no `.sdd/graph` is counted under `graph`.
4. A code repository with a stray empty `.sdd/graph` and a code-repository `graph_dir` pointing elsewhere, and no `project_dir`, reads its own `.sdd/graph`.
5. With neither key, the gate reads `.sdd/graph` as before.
6. In a code repository with `project_dir`, `agentic-memory new --link <id>` of a graph-repository entry links, its status flag reads from that graph, entries take the graph repository's `language`, and the store key is the graph repository's `repo_id`.
7. `docs/grounding-gate/architecture.md`, `docs/memory/architecture.md` and `docs/capture/usage.md` name the resolved graph project.
