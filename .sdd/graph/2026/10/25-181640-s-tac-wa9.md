Done for 20261025-165016-d-tac-9xz: commit 81df9dd, released as v2.2.2 (release commit fb226df).

- `plugin/hooks/run` writes the fetching process's pid to `.fetch-<version>/owner`; `HUP`, `INT` and `TERM` traps remove the lock and kill the download, which runs in the background so `wait` lets the trap fire at once; a waiter finding the owner gone takes the lock over at once, a `.fetch-<version>.takeover` directory keeping two waiters from both doing so; the five-minute rule applies only to a lock without an `owner` file.
- Tests: the signal table (`TestAFetchSignalledMidDownloadLeavesNothingBehind`, which also checks the download stops), `TestALockWhoseOwnerIsGoneIsTakenOverAtOnce`, `TestAFetchKilledUncaughtIsTakenOver` (SIGKILL), `TestALockOfALiveFetchIsWaitedOn`; parallel fetches still fetch once.
- Guards: each signal trap alone, the background download, the dead-owner check, the owner write, the age rule and the fetch after a takeover were each broken and caught. An `EXIT` trap was removed: the signal traps masked it fully and its only other path was a `set -u` abort. Clearing the traps in `unlock` is unreachable by a test (a race with another process's lock).
- 2.2.2 fetched cleanly on this machine afterwards, no lock left behind.
- Docs: README.md described the owner file and the trap in 81df9dd itself; since dfd13bd moved every piece's internals out of the README, that description lives in `docs/plugin/architecture.md`, "The fetch lock".
