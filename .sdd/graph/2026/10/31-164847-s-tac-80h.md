Shell-guard counts the input of a piped shell inside a compound command as replaced only when every redirection onto descriptor 0 is a here-document or here-string, and a numbered redirection reaches descriptor 0 only when its number parses to 0, in agentic-helpers commit ce226ab, not yet released, building on 20261031-163018-s-tac-ptl. It replaces 20261031-164457-s-tac-sxd (commit a06dd2d), whose rule read a number that does not parse as descriptor 0: a named descriptor (`{fd}<<< 'echo hi'`, which the parser gives as `{fd}`) is a new one the shell allocates, so stdin stayed the pipe while its here-string counted as replacing it, and `echo 'rm x' | { sh {fd}<<< 'echo hi'; }` ran unjudged.

The full rule in `internal/shellwalk`'s `redirectsInput`: an unnumbered redirection reaches descriptor 0 only through an input operator, a here-document or a here-string; a numbered one reaches it when its number parses to 0 (`0`, `00`), any operator included (`0>&3` duplicates as `0<&3` does); a named descriptor never does, and skipping it can only leave the shell counted as reading the pipe. Any redirection reaching descriptor 0 that is not a here-document or here-string (a file, since any name may be a link to `/dev/stdin`, or a duplicate) keeps the shell reported as reading the pipe, and every one counts, since zsh's MULTIOS feeds them all. Accepted cost: `echo x | { sh < script.sh; }` is refused, as `sh < file` at a pipe's end already was. Each check, broken in turn, made its own test fail, and restored, passes; `docs/shell-guard/architecture.md` states the rule.
