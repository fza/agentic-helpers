agentic-tools keeps tool vectors in the segment store `internal/vectorseg` that agentic-memory adopted (20261027-130307-d-tac-wd3), in place of the vector kept per tool in every store's `index.json` and the whole-file cache `~/.cache/agentic-tools/vectors/<fp>.json`, both from the tools directive (20261025-185701-d-tac-e9x).

- **Layout.** `~/.cache/agentic-tools/vectors/<fp>/`, one directory per embedder fingerprint, holding vectorseg segments. A row's id and hash are both the tool's `described` hash, so one vector serves every store naming that description, as the cache keyed by description does today.
- **A write is one segment.** `add`, `update`, `merge` and a rebuild file one segment holding only the rows they embedded, then merge under the store's lock.
- **Liveness.** A row counts while some store on the machine names its description, read from every store's index whatever `AGENTIC_TOOLS_SCOPE` says; a merge drops the rest.
- **`index.json` schema 2** carries no `vector` and no `fingerprint`: the segment directory already names the embedder.
- **Reads.** `find --query`, `add`'s near-duplicate check and the prompt offer score through one mapped snapshot, a tool scoring by the row of its description.
- **Migration.** An existing `<fp>.json` becomes one segment and is removed, with no embedder call.

Why: today every prompt hook decodes each store's `index.json` whole, vectors included (one store's is 480 KB for its tools), and every write rewrites both the index and the cache whole, so each tool added slows every later prompt and write.

Rejected:

- Keeping vectors in `index.json`: every read decodes them, every write rewrites them.
- A row per store and tool name: one description embedded and stored again in every store holding it.
- Keeping every row forever, as the cache does today: the store grows by every description ever embedded.

Accepted costs: a store left on schema 1, another project's whose own session has not written it since, is rebuilt from its tool folders on each read until it is; a merge reads every store's index; a process writing the cache can plant vectors that skew ranking, as it can today (20261025-185324-s-tac-k4o), but a planted row never surfaces a tool no store names.

Done when tests show a write rewriting no vector file whole, `index.json` holding no vector, the cache migrated with no embedder call, a description no store names merged away, and find, the near-duplicate check and the offer ranking as before, each guard broken and watched failing; `docs/tools/architecture.md` describes the layout.
