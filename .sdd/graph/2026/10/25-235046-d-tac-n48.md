shell-guard becomes an agentic-helpers piece: a `PreToolUse` hook on `Bash`, `agentic-shell-guard`, that holds an agent's removals to the project and bans `mktemp`. It carries every rule of the machine-level guard kept under `~/.claude/managed-policy/shell-guard/`, which installs root-owned as managed policy and so reaches no other machine; once the plugin carries it, that policy copy retires.

Why: a stray `rm -rf` outside the project is the one mistake an agent cannot undo, and a careless chain such as `cd ~ && rm -rf x` slips past any rule that reads targets without parsing the command. The guard parses the command as bash, so `rm` inside a quoted argument (a sed script, a commit message) is text and passes, while code handed to `eval` or a shell's `-c` is parsed again.

**Guards and their plugin options.** Every guard is on by default and has its own `userConfig` key:

| Option | Values | Default | Judges |
|---|---|---|---|
| `shell_guard_outside_project` | `ask`, `deny`, `off` | `ask` | a removal (`rm`, `rmdir`, `unlink`, `git rm`) whose target lies outside the project root and `/tmp`, or is the root or `~` itself |
| `shell_guard_find_delete` | `ask`, `deny`, `off` | `ask` | `find ... -delete` |
| `shell_guard_lone_removal` | boolean | `true` | a removal that is not the whole command: no other statement, pipe, redirection, subshell or wrapper |
| `shell_guard_expansion` | boolean | `true` | a removal target built from a variable or command substitution |
| `shell_guard_nested_code` | boolean | `true` | a removal or `mktemp` inside `eval`, a shell's `-c`, or inline code for another interpreter (`perl -e`, `python -c`, `node -e`, ...) |
| `shell_guard_mktemp` | boolean | `true` | `mktemp` anywhere in the command |

A boolean guard denies when on. A command that does not parse as bash is denied whatever the options say: the guard cannot judge it.

- **Ask or deny for the outside-project guard is the user's choice.** A hook's `deny` holds in every permission mode, `bypassPermissions` included; its `ask` forces a prompt even in auto mode, labelled `[plugin:agentic-helpers]`. `ask` keeps cleanups outside the project possible with the user's approval; `deny` suits unattended runs, where the user runs such a removal as `! rm ...`.
- **A switched-off supporting guard falls to the outside-project verdict.** `shell_guard_lone_removal`, `shell_guard_expansion` and `shell_guard_nested_code` are what make the outside-project check sound: without them a removal's target cannot be placed before it runs. With one of them off and `shell_guard_outside_project` not `off`, a removal it no longer denies takes the outside-project verdict, reason `cannot place: <target> (<why>)`. Both off, it runs.
- **The `mktemp` refusal points at `.tmp/`**, the directory the scratch sweep owns, and where the project has none, says to create it.
- **Refusals start `agentic-shell-guard: `** and are part of the hook's contract; the skill quotes them.
- **A missing binary fails closed**, as the grounding gate's does: `plugin/hooks/run` refuses the call, naming the release it could not fetch.

**It judges every project.** Every other piece stays silent until a project carries the directory it needs or a session claims a seat. shell-guard's work is every Bash call, so it has no such directory; the principle reads "silent where it has nothing to work on" and shell-guard always has something. A user who wants it off turns its options off.

**It guards against mistakes, not against an agent set on getting around it.** The plugin can be disabled in user settings and its binary lives in the plugin's user-writable data directory. A machine that wants it locked on force-enables the plugin and pins the `shell_guard_*` options through managed settings (`enabledPlugins`, `pluginConfigs`); `docs/shell-guard/usage.md` shows how.

**Surfaces:** binary `agentic-shell-guard` under `source/hooks/cmd/`, package `source/hooks/internal/shellguard`, a `PreToolUse` `Bash` entry in `plugin/hooks/hooks.json`, the six `userConfig` keys above in `plugin/.claude-plugin/plugin.json`, skill `agentic-helpers:agent-shell-guard`, `docs/shell-guard/usage.md` and `architecture.md`, and the dependency `mvdan.cc/sh/v3` in `source/hooks/go.mod`, which parses bash and is the only way to tell a removal from text that names one.

Rejected:
- **Only the removal rules, leaving `mktemp` to the machine's policy.** Two guards on one machine, one of them outside the plugin.
- **`ask`, `deny`, `off` on every guard.** Values like `ask` on `mktemp` mean nothing, and each one is a test case.
- **Supporting guards forced on while the outside-project guard is on.** An option that sometimes does nothing.
- **Supporting guards independent, hole documented.** The outside-project promise would hold only with all three on.
- **A root-owned `install-policy` subcommand writing managed settings.** Needs `sudo` and is a second install path outside the plugin, which installs at user scope.
- **Opt-in per project through a marker directory.** No protection in a project that has not opted in, which is where a stray removal does its damage.
- **Names `removal-guard` and `bash-guard`.** The first does not cover `mktemp`; the second reads as a guard for the bash program.

Accepted costs: the plugin acts in every project by default; an agent with write access to `~/.claude` can swap the binary; `source/hooks` takes its first parser dependency.

## Acceptance criteria

- `agentic-shell-guard` answers a `PreToolUse` `Bash` payload with `deny`, `ask` or nothing, and `plugin/hooks/hooks.json` wires it for `Bash`.
- With no options set, every guard is on with the defaults in the table, and the verdicts match the machine-level guard's on its test cases.
- Each of the six options, set to each of its values, changes only its own guard's verdict, with a test per value.
- With `shell_guard_lone_removal`, `shell_guard_expansion` or `shell_guard_nested_code` off and `shell_guard_outside_project` set to `ask` or `deny`, `cd ~ && rm -rf x`, `rm -rf "$HOME/x"` and `bash -c 'rm -rf ~/x'` respectively get that verdict with a `cannot place:` reason; with `shell_guard_outside_project` off as well, they pass.
- An unparsable command is denied with every option off.
- The `mktemp` refusal names `.tmp/`, and in a project without `.tmp/` says to create it.
- A missing `agentic-shell-guard` binary refuses the call through `plugin/hooks/run`.
- `docs/shell-guard/usage.md` and `architecture.md` exist, `usage.md` shows locking the plugin on through managed settings, and `README.md` and `AGENTS.md` state the silent principle so that it covers shell-guard.
- The skill `agentic-helpers:agent-shell-guard` quotes every refusal reason as the binary prints it.
