agentic-memory and agentic-tools save the vectors of each embedding request as it answers, instead of only once every missing text has answered. A fill splits the missing texts into groups of whole entries or tools, each at most `embed.RequestTexts` texts (the smaller of the OpenAI and Ollama request sizes, so one group is one request), embeds and writes each group in turn, and stops at the first failure with every earlier group kept.

**Why.** `fill` in `source/hooks/internal/memory/vectors.go` and `source/hooks/internal/tools/vectors.go` sends every missing text in one call bounded by `embedding_timeout` (default 2m), or 5s in a hook, and writes nothing unless all of it answers. A whole-store re-embed, which every fingerprint change (model, dimensions, templates) causes, that takes longer than that bound is thrown away and sent again in full by the next search, recall or filing, so it never lands while it loads the embedder each time. A store of 4,600 texts at 100 per request and 3.6s per request needs 166s.

**Rejected.**
- A longer timeout: any bound a larger store or slower embedder outgrows fails the same way.
- A background re-embed process: a new long-running process and its lifecycle for what saving per request already solves.

**Accepted costs.** A large re-embed writes one segment per request, which the store's merge folds as it already does; a search during a partial re-embed still fails as before until the rest lands.

**Acceptance.**
1. A fill that fails partway keeps every group answered before the failure; the next fill embeds only what is still missing.
2. Both memory and the tool library behave so.
3. Tests cover each, and each new guard is broken once to watch its test fail.
