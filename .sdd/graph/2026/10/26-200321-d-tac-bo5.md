Where sdd's engine is reachable, a capture runs through it: `mcp__sdd__start_procedure` with `canonical: capture`. `agentic-capture` (20260925-153653-d-tac-piz) is the capture path only where it is not: no sdd MCP server, or one that refuses the graph.

**The skill says it.** `agentic-helpers:agent-capture` gains the split at the top of its description and its body, in place of its rule that every capture runs through `agentic-capture`: `mcp__sdd__*` tools present → the engine's `capture` procedure through the `sdd` skill; `agentic-capture` otherwise. sdd's `sdd` skill is the engine flow; nothing names the deprecated `sdd-engine`.

**The gate holds it.** A `Bash` call running `agentic-capture`, recognised in every spelling 20260925-193337-d-tac-9jv covers, is refused while the project's `.mcp.json` declares `mcpServers.sdd`, whatever reads the session holds. The refusal names the MCP capture to use instead. `cli_capture: true` in `.sdd/grounding.yaml`, read from the resolved graph project (20261026-195422-d-tac-g3w), lifts it for a project that captures through `agentic-capture` on purpose. The MCP capture keeps owing the reads it owes (20261025-020550-d-tac-ofh). A plain `sdd new` keeps its current rule.

Why: the engine's capture procedure carries what `agentic-capture` lacks: a writing-guide review, a playback of the exact entry the owner confirms, and a check of the generated summary. In a `gvb-mika-sdd` session with the engine installed, the agent made all 9 captures through `agentic-capture`: 6 decisions entered the graph without their text shown to the owner, a `[medium] missing-ref` pre-flight finding went unmentioned, and summaries were fixed by hand afterwards. The `agent-capture` skill, loaded before every capture, directed every capture to `agentic-capture` and named no engine. In a `gvb-mika` session the agent loaded that skill, then used the engine anyway: the right path, reached against the skill's text.

Rejected:

- Skill text only: rests on the agent reading the skill, which already sent one agent the wrong way.
- A confirmation flag on `agentic-capture` (the owner's approval of the draft's hash): duplicates the engine's playback without its writing-guide review or summary check, and breaks every existing caller.

Accepted costs:

- A new refusal: every skill and doc quoting the gate's refusals changes with it.
- A project whose `.mcp.json` declares an sdd server that fails to start is refused until the server is fixed or `cli_capture: true` is set.
- An sdd server configured outside `.mcp.json` (user or local scope) goes unseen, and `agentic-capture` passes there.
- Projects capturing through `agentic-capture` beside an sdd server (pipelines, scripted captures) set `cli_capture: true`.

Acceptance criteria:

1. With `.mcp.json` declaring `mcpServers.sdd` and the three reads credited, `agentic-capture d.md` is refused with the engine refusal, naming `mcp__sdd__start_procedure`.
2. The same with `cli_capture: true` in `.sdd/grounding.yaml`: the capture is gated by the reads as today.
3. Without an sdd server in `.mcp.json`: gated by the reads as today.
4. `agentic-capture --help` and a bare mention pass.
5. `agentic-helpers:agent-capture`'s description and body state the split; `docs/capture/usage.md`, `docs/grounding-gate/usage.md`, `docs/grounding-gate/architecture.md` and `agentic-helpers:agent-grounding` describe the refusal and `cli_capture`.
