agentic-memory's Stop hook delivers every hold (pending do-now items, shipped work since the last state write, the filing backstop) as Stop context: `hookSpecificOutput.additionalContext` on stdout with exit 0, in place of the text on stderr with exit 2. The holds' wording, order and firing rules stay as they are; only the delivery changes, starting with the shipped-work hold of 20261027-222420-d-tac-ac7, which named exit 2.

Why: Claude Code draws a Stop hook's exit 2 as a `Stop hook error` line in the user's default view, quoting the hook's path and the whole hold, after every turn that ships work. A Stop hold is a message for the agent alone (20261027-222117-d-tac-yjy). Claude Code's hook documentation states that Stop `additionalContext` keeps the turn going through the same loop guards as a block (`stop_hook_active`, the cap on consecutive continuations), reaches the agent as a system reminder, shows no hook error, and appears only in the transcript view as `Stop hook feedback`. The grounding gate moved its let-through note to `additionalContext` for the same reason (20261025-161257-d-tac-ega).

Rejected: `decision: "block"` with a `reason`, which the same documentation draws as a hook error; shortening the hold texts, which leaves the error line; dropping the holds, which loses the state writes and owed rules they secure; falling back to exit 2 when the context cannot be written to stdout, a guard no test can reach.

Accepted cost: a hold is invisible to the user unless the transcript view is open, so a user no longer sees why the agent takes one more turn.

Acceptance criteria:

1. Each hold exits 0 with its text as Stop `additionalContext` and nothing on stderr, checked per hold by tests that fail when the hold goes back to exit 2.
2. A Stop that holds nothing prints nothing.
3. A live session on the built binary takes the shipped-work hold as context, and the user's default view shows no Stop hook error.
4. `docs/memory/` and `agentic-helpers:agent-memory` name the delivery, in the same change.
