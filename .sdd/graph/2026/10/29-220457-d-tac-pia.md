Agentic-memory stores a due time (20261029-200931-d-tac-8h5) as a new `due` row in the memory log, which raises the store format from 6 to 7. Moving or clearing a due time after filing is an event, and the log keeps every event as a typed row: a release meeting a row kind it does not know reads the store as corrupt (`internal/memorylog/tail.go`), so a new kind cannot arrive silently.

What changes:

- `memorylog` gains the kind `due`, appended to the kind list whose index is the segment encoding. Its payload is the due time, or none for a clear.
- `new --due` files the time in the `new` row's payload; `due <id> <time>` and `due <id> --clear` write a `due` row.
- The first call of the new release on a format-6 store copies the log to `backup/format-6-<UTC stamp>/` and writes `format.json` as 7, under the store lock, the way format 5 arrived for todolist items. Nothing in the log is rewritten.

Accepted cost: once one session runs the new release, every session still on an older agentic-helpers release refuses memory calls with "a newer store" until its plugin reloads, in every project on the machine, the fdbox board jobs included. Older binaries restarting after a store migration is accepted precedent (20261025-181442-s-tac-5fz).

Rejected alternatives:

- The due time at filing only, in the `new` payload, which older releases ignore: no format bump and no lockout, but a due time could never move or clear, the `due` command and MCP tool would go, and an agent would refile with `--absorbs` to change a date.
- Riding an existing row kind: every candidate changes state in an older release (`retain` resets the decay, `confirm` re-anchors, `settle` feeds the do-now logic).
- Deferring the due time to the next planned format bump: none is planned, so the feature would wait indefinitely.

Acceptance criteria:

1. A format-6 store is backed up and moved to format 7 by the first call, once, under the lock; two concurrent calls migrate once.
2. A binary of this release refuses a format-8 store as newer; a format-7 store with `due` rows folds them in order, the last one standing.
3. A merge of sealed segments keeps an entry's latest `due` row.
