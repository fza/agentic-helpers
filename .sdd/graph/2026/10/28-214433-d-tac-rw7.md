Only agentic-memory and agentic-tools serve MCP tools; every other agentic-helpers binary stays a hook or a command run through Bash, and gains no MCP server.

- `agentic-scratch`, `agentic-grounding-gate` and `agentic-shell-guard` are hooks only (`start|end`, `record|gate|start|end`, `permission|output`): nothing in them is for an agent to call.
- `agentic-helpers` keeps `check` and the `config` commands of d-tac-cld as Bash commands. An MCP server for them would run one more process for every open session (an idle `agentic-tools mcp` measures 4 to 8 MB here) for commands used a few times a month, and would be one more server held in step with its command line. Folding its tools into the `memory` server instead would put configuration under memory's name and switch it off whenever `memory_enabled` is off, as d-tac-yrx turns an off piece's server down.
- `agentic-capture` stays a command. It serves only projects without sdd's engine, where the engine's own MCP capture is not available; its pre-flight can run for minutes and retries, so a tool call would outlive the client's tool timeout and continue in the background; and the grounding gate, which finds a capture by parsing the Bash command, would need a second check for an MCP tool.

The pieces and their surfaces are those s-cpt-ihb lists.

This is settled: it adds nothing to build and records why the binaries outside memory and tools have no MCP server, so the question is not reopened without a new reason, such as an agent that runs no Bash.

**Rejected.** An `agentic-helpers` MCP server with `check` and `config` tools; those tools inside the `memory` server; an MCP capture tool.

**Accepted costs.** An agent changing a setting for the user runs `agentic-helpers config set` through Bash; capture in a project without sdd's engine stays a command.
