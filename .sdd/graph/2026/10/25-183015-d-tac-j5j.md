agentic-memory's `supersede`, `confirm` and `retain` take several entry ids, as `retire` does, and `new --absorbs <id>...` supersedes named entries by the entry it files. Every batch is checked whole against one load of the log and lands in one append, or nothing lands.

**The verbs.**

- `agentic-memory supersede <id>... --by <id> | --because '<why>'`, MCP `supersede` with `ids` (array) in place of `id`.
- `agentic-memory confirm <id>...`, MCP `confirm` with `ids`.
- `agentic-memory retain <id>... <level>`, the last positional the level, MCP `retain` with `ids` and `level`.
- `agentic-memory retire <id>... [--because '<why>']`, unchanged in form, now all or nothing.
- `agentic-memory new ... --absorbs <id>`, repeatable, MCP key `absorbs` (array): the filed entry supersedes each named one `--by` itself, in the same append as its `new` event.

**All or nothing.** A batch loads the log once and checks every id: it exists, the caller may change it, its state allows the change. Any failing id refuses the whole call, exit 1, naming every failing id:

    agentic-memory: nothing superseded:
      m-b is already superseded
      m-c belongs to main

Otherwise every event lands in one `appendEvents` call and the reply names each id: `superseded m-a, m-b, m-c by m-d`. `new --absorbs` refuses the filing the same way when an absorbed id fails, the second case beside an unresolved `--link` where `new` does not land.

**The defect this closes.** `retire` today applies ids one at a time and on the first failure returns only that failure (`source/hooks/internal/memory/lifecycle.go:64-74`): ids before it stay retired while the reply never says so.

Why: folding several notes into one summary took one call per note, each loading the whole log again. A batch is one call, one load, one append. Partial application leaves a state the agent must reconstruct from an error message; a whole-or-nothing batch leaves either the old state or the asked-for one. `--absorbs` turns filing a summary and pointing its parts at it into one call.

Rejected:

- Best effort with a per-id report: half-applied state under exit 1, read back from the reply.
- A ready `ToolSearch select:` line printed at SessionStart and claim, loading the memory tools in one call: tokens on every start, and names that go stale when a tool is renamed.
- One `memory` MCP tool taking an `op` field: loses each tool's exact-key schema (20261025-034140-d-tac-9os).
- An `absorbs` list declared on the summary and applied later: two writes for one intent.

Accepted costs:

- One bad id blocks the good ones; the agent sends the call again without it.
- `supersede`, `confirm` and `retain` change their MCP key from `id` to `ids`, a breaking change on the MCP wire; the CLI keeps the single-id form as a batch of one.
- `new` refuses a filing over a failing `--absorbs`.

Acceptance criteria:

1. `supersede m-a m-b --by m-d` supersedes both in one append; `confirm m-a m-b` and `retain m-a m-b long` likewise; `show` of each reflects the change.
2. A batch with one id already superseded, retired or owned by another seat (for the owner-only verbs) exits 1 with `agentic-memory: nothing <verb>:` and one line per failing id, and the log is byte-identical before and after.
3. `retire m-a m-b` with `m-b` already retired retires neither and names `m-b`; a successful `retire` reply names every id.
4. `new --absorbs m-a --absorbs m-b` files the entry and supersedes both `--by` it in one append; with `m-b` already superseded nothing is filed and `m-b` is named.
5. The MCP `supersede`, `confirm` and `retain` tools take `ids` and refuse `id`; `new` takes `absorbs`; each schema carries `additionalProperties: false`.
6. `docs/memory/usage.md`, `docs/memory/architecture.md` and `agentic-helpers:agent-memory` show the batch forms, `--absorbs`, and the all-or-nothing rule.
