Several state files of the hooks can be published torn when two hook processes write them at once.

Observed, by reading the code: the agentic-memory caches beside the log of the agentic-memory directive (20261025-014326-d-tac-mvn) write through one fixed temporary name before renaming: `memory/cache.go:57` (`heat.json` and the other JSON caches), `memory/vectors.go:93` (`vectors.gob`), `memory/format.go:54` (`format.json`) and `seat/shelves.go:148` (`shelves.json`), each `path + ".tmp"`. Two writers interleave in that one file and the second rename publishes a mix. The grounding gate's ledger is written in place with `os.WriteFile` (`grounding/ledger.go:193`), so a reader can see it half written. The hooks of one event run in parallel, so concurrent writes are the ordinary case, not a corner.

Expected: a reader only ever sees a whole file, the old one or the new one. The store already writes that way where it matters most: `memorylog.replaceFile` (`memorylog/memorylog.go:379-406`) writes a unique temporary file with `os.CreateTemp` in the target's directory, syncs it, renames it over the target and syncs the directory. The unlocked read-modify-write race on `heat.json` that 20261025-034001-d-tac-bf0 accepted loses warms; it does not cover a torn file.

What a torn file costs: a torn `heat.json` resets the brief's order; a torn `vectors.gob` re-embeds the whole store; a torn ledger makes the gate refuse for want of reads the session made.

Candidate remedy, not decided here: one shared helper on the `replaceFile` pattern, used by every write above, with the standard library alone.
