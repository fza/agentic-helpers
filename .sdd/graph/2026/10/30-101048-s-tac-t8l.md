Tool links on agentic-memory entries are built in agentic-helpers commits 2adbab6 and fd1abd4, not yet released, closing the directive (20261030-002417-d-tac-s6o).

`new --tool <name>[@<project>]`, `link <id> --tool` and `unlink <id> --tool` resolve the name as `agentic-tools take` does and refuse one resolving to nothing, or every one while agentic-tools is off. A link is a `link` event whose target is `tool:<name>`, with the store key for another project's tool, so releases reading the same log keep working. Every line carries `→ tool <name>`, `gone` or `merged into <survivor>` where that applies, and the short line of `agentic-memory brief` and recall keeps it listed rather than counting it among ended links. `show` takes each named tool through `tools.Linked.Take`, records the session's holding, counts no taker, and prints the section under `tool (registered by other agents):`, adding the foreign mark for another project's tool and a `(seen)` pointer once the context holds the usage. JSON reads carry `tools`.

One deviation: `link` and `unlink` take `tool` as an array of one over MCP, since the request field is shared with `new`.

Proof: `internal/memory/toollinks_test.go` covers every acceptance criterion, and each of its 16 guards was broken and caught. The race suite passes. Live on the installed build, an entry filed with `--tool citation-relink@format-d-fdbox` showed `→ tool citation-relink@format-d-fdbox`, and `show` copied the tool to `.tmp/tools/citation-relink@format-d-fdbox/v1` with the foreign mark and its usage.
