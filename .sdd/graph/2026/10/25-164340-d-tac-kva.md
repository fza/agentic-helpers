The grounding gate lets a `NotebookEdit` call through with the `additionalContext` note, as it does `Write`, `Edit` and `AskUserQuestion`; it never refuses one. The gate already guards `NotebookEdit` (`gatedTools` in `internal/grounding/grounding.go`), and the let-through set is every tool there whose refusal Claude Code draws red: `AskUserQuestion`, `Write`, `Edit`, `NotebookEdit`. Every refusal on `Bash` and on the `sdd` MCP tools stays one.

Why: measured in Claude Code 2.1.310 by fdbox with a probe hook, a refused `NotebookEdit` draws red in the default view, for exit 2 and a JSON `deny` alike, as `Write` and `Edit` do. A refused `Read`, `Grep`, `Glob` or MCP tool call folds into a grey line (`Read 1 file`, `Searched for 1 pattern`, `Called plugin:...`) and shows red only in the ctrl+o view, so the gate's MCP capture refusal and short `mcp__sdd__show` refusal stay refusals. A `PostToolUse` exit 2 draws two grey lines; an allowed call with `additionalContext` stays silent on every tool.

Rejected: leaving `NotebookEdit` a refusal (the one red line the let-through set was meant to remove would remain for notebooks).

Accepted costs: a notebook edited without the reads is not stopped, only noted, as for `Write` and `Edit`.

Acceptance criteria:

1. A `NotebookEdit` payload with reads owed exits 0 with `additionalContext` opening `GROUNDING GATE: let through, reads owed.`
2. The let-through set and `gatedTools` agree: a test fails if a gated tool outside `Bash` and `mcp__sdd__*` can still be refused.
3. `README.md` and `agentic-helpers:agent-grounding` list `NotebookEdit` among the let-through tools.
