Claude Code refuses a plugin manifest whose `userConfig` option declares `options` (a picker) without also declaring a `default` among those values or `required: true`: `claude plugin validate .` (Claude Code 2.1.314) reports `a field with options needs a default among them, or required: true` for each one. The picker half of the directive on pickers and bounds (20261030-083534-d-tac-ws7) cannot be built as written, since that directive keeps the no-declared-defaults rule of 20261028-212647-d-tac-cld.

Both ways the manifest allows break that rule:
- A declared `default` reaches every hook as an answer, so the option's value would always come from the agent layer and `config.yaml` would never decide it.
- `required: true` makes the dialog refuse an empty value, so enabling the plugin forces the user to answer every picker, and that answer hides `config.yaml` the same way.

The affected options are `embedding_source`, `embedding_provider`, `writing_style`, `scratch_sweep`, `shell_guard_outside_project`, `shell_guard_find_delete`, `shell_guard_secrets` and `shell_guard_secret_output`. They stay plain text fields whose descriptions list their values. The bounds half of ws7 is built: every number option declares `min` (and `max` where the reader has one), and `internal/plugin/options_test.go` checks each against the option reader. With no picker declared, the manifest needs no minimum Claude Code, and README states none.

An owner decision is needed: give up pickers, accept a declared default for some keys (losing `config.yaml` for them), or something else.
