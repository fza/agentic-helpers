The shared credential fixtures of `github.com/fza/agentic-helpers` are stored base64-encoded, and its unpushed history was rewritten to match, because GitHub push protection refused every push holding them in plain form (`source/hooks/test/fixtures/secrets/`, from the credential scanner directive 20261026-223236-d-tac-vr7), even with `.github/secret_scanning.yml` listing `paths-ignore: ["source/hooks/test/fixtures/secrets/**"]` on the default branch `main`. Observed on 2026-10-27 through `git push` and the repository settings read with `gh api`.

- With the repository's secret scanning off, the block came from push protection for the pushing user's account, which covers every public repository and does not read the repository's `secret_scanning.yml`.
- With the repository's secret scanning and push protection switched on, the block stayed, now as `GH013: Repository rule violations`, across three retries over about eight minutes. So for this repository a file on the default branch did not exempt the fixtures, as the superseded fact expected; why it did for `github.com/fza/sdd`, whose settings and file match, is not known.

What holds now: the fixtures are stored base64-encoded, each `<name>.b64`, and the `test` package decodes them on load (`SecretFixtures`, `SecretFixture`, `Fixture` for `secrets/` names), so no committed blob holds a token. The 70 commits from 972b834 to the then tip of `main`, none pushed before, were rewritten that way before the first push, which landed as `cf06f03`. Every rewritten commit got a new hash; graph entries citing the old short hashes resolve through the attached list, old hash to new hash with each subject.
