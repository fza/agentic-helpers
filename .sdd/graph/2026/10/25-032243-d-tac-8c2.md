A merge of the agentic-memory log (`mergePolicy`, `internal/memory/state.go`) bounds what it keeps of old history, so the merged segment grows with the entries a project holds rather than with every event ever appended.

**Fold.** Every event older than 14 days (`supersedeKeep`, the revive window) is folded: an entry's events before that horizon are rewritten as the shortest run of existing event kinds that rebuilds its state at the horizon. That is one `new` row (the entry's id, seat, session, filing time, branch, commit and anchors, with its title, topics and retention as they stand at the horizon and its body), then its latest `confirm` where one exists, then its latest `retire` or `supersede` where the entry is not live at the horizon, each at its own time and seat. Events after the horizon follow unchanged. `merge` events (topic merges) are kept as they are. No event kind is added, so a binary of an earlier release reads a folded log.

**Retired bodies.** A merge strips the body of an entry retired longer ago than `retired_body_days`, as it already strips one superseded longer ago than 14 days: `body` empty, `dropped` set. `retired_body_days` is a `userConfig` number in `plugin/.claude-plugin/plugin.json` beside `entry_max_words`, read by `internal/pluginconfig`, default 90, a value below 14 read as 14. The entry still shows in search, flagged retired, by title and topics; `show` prints `(body dropped 90 days after the retire)`, the number the setting's; `revive` of such an entry is refused with `<id> body dropped; file it again`, as for a superseded one.

Why: the tail is already bounded (sealed past 64 KiB, merged at eight segments), but the merged segment kept every event of every entry, so retitles, tags, confirms and retention changes accumulated without bound, and a retired entry's body stayed forever though it never reaches the brief again. Every reader of event history works inside the 14-day horizon (`revive`, the 14-day supersede body drop, the brief's "changed by other seats" since the seat's last brief), so a fold past it changes no answer the tool gives within that window.

Rejected: a new event kind for a folded entry. Cleaner to read, but an earlier binary indexes `kinds` by the segment's kind byte and fails on one it does not know, and sessions running an earlier release share the store. Rejected: folding every event at every merge, horizon or not. It would break `revive` and the brief's changes for recent events. Rejected: leaving growth unbounded. Rejected: dropping retired entries outright. Search would lose the flagged pointer to work that was done.

Accepted costs: `show`'s event list loses every event older than 14 days except those the fold keeps; a seat not briefed for more than 14 days misses other seats' changes from before the horizon; a retired finding wanted back after 90 days must be filed again; each merge still rewrites the whole merged segment.

Acceptance:

- A merge of an entry retitled, tagged, retained, confirmed twice and retired, every event older than 14 days, leaves one `new` row carrying the latest title, topics and retention, the latest `confirm`, and the `retire`; the folded state equals the unfolded one.
- Events younger than 14 days survive a merge unchanged, and `revive` of an entry retired or superseded within 14 days still works after a merge.
- `merge` events survive every merge.
- A merge strips the body of an entry retired more than `retired_body_days` ago and keeps one retired more recently; `revive` of the stripped one is refused with `body dropped; file it again`.
- `retired_body_days` unset reads 90; 7 reads 14; 120 reads 120.
- A log folded by the new binary is read by the previous release's decoder without error (a segment holding only the existing kinds).
- `README.md`, `agentic-helpers:agent-memory` and the plugin's `userConfig` describe the fold and the setting.
- Each new guard is broken, its test watched failing, and the file restored byte-identically.
