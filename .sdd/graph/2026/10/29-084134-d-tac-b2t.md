The rule of 20261028-212647-d-tac-cld that keys deleting stored data live in `config.yaml` only covers just agentic-helpers' own stored data shared by every agent (memory, tools, attachments); a key deleting a session's own work file stays overridable per agent. `capture_remove_draft` (20261029-023740-d-tac-yl8) deletes only the capture's own draft, so it stays an overridable key, default true, once the `config.yaml` layering lands: `config.yaml`, then the agent's own option, then managed settings.

- **In scope** of the `config.yaml`-only rule: keys deciding when shared stored data goes, such as `retired_body_days`, `temporary_seat_lifetime`, `orphan_store_grace` and `tools_total_mb`.
- **Out of scope:** keys deleting what one session made for itself, today `capture_remove_draft`. They stay declared in the plugin's `userConfig` (`plugin/.claude-plugin/plugin.json`), the agent's own option layer for Claude Code, and so in its plugin dialog.
- **Docs.** README's `Options` and the `docs/` pages describing the layering state the rule with this scope.

Why: cld keeps deleting keys out of the agent's layer so that one agent's setting cannot purge data other agents share, whichever process runs the cleanup. A draft belongs to the session that wrote it, so no other agent's data is at stake.

Rejected: `capture_remove_draft` in `config.yaml` only (no switch in Claude Code's plugin dialog, and one value for every agent on the machine).

Accepted cost: the rule that deleting keys live in `config.yaml` carries a stated scope a reader has to know.

Acceptance: `capture_remove_draft` set as a Claude Code plugin option overrides `config.yaml`; README `Options` states the scope of the `config.yaml`-only rule.
