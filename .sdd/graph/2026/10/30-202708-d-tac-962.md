The `agentic-memory new` reply, on the command line and over the memory MCP server alike, drops the echo of what the caller just sent: its first line becomes `filed <id>` followed only by the entry's flags, and the MCP answer is `{"message": <that text>}` alone, without the typed fields 20261027-180531-d-tac-04v added beside it.

**Why.** Every `new` reply said everything twice. The text line repeated the title, seat, kind, source, filing time and commit the caller had just sent or could not act on, and the typed fields (`id`, `title`, `kind`, `topics`, `superseded`, `attachments`, `not_linked`, `near_topics`, `similar`) repeated the text again, empty lists and 16-digit scores included; 20261029-130234-d-tac-s4c trimmed read answers this way but left write answers as they were. Measured over the 42 `new` replies of this shape in three days of transcripts: 15.6k characters as sent, 12.5k with empty keys dropped and scores as integers, 6.8k as `message` alone, 2.3k as `message` alone with the echo cut, an 85% saving on a call every seat makes many times a session. Under the token-cost criteria of 20261029-021515-d-tac-00q the last option loses nothing an agent acts on: the new id, the entry's flags (declared ends, due time, link states), superseded ids, attachment lines, unresolved ids, todo item ids, the list-lines note, body and title notes, near topics with their merge, similar entries and forbidden-pattern hits all stay in the text.

**What stays on the first line.** `filed <id>`, then the flags `line` prints today after the bracket (`until:`, `due`, `when:`, link and anchor states), since those carry the normalized or computed form of an input rather than the input itself. The bracket (seat, recipients, kind, retain override, `from`, time, commit) and the title go.

**Scope.** `new` only. The other write tools keep the message-plus-fields answer of 20261027-180531-d-tac-04v until measured on their own; reads keep the compact JSON of 20261029-130234-d-tac-s4c. Since the plugin's MCP readers are agents and its own skills, it ships as a minor release (a `feat:` commit), as 20261029-131013-d-tac-xcu set for the read trim: its readers update in the same change, and a major release would hold the saving back for a contract change few readers notice.

**Rejected.**
- Drop empty keys and use integer scores only: keeps 04v intact but saves 20%, leaving every reply twice over.
- `message` alone with the echo kept: saves 56%, but still repeats the caller's own input on every filing.
- Typed fields alone: the hints carry wording the skill quotes (`similar:`, `new topic ... near:`, `items <id>:`), and an agent reads text as readily as keys.
- Leaving it: about 370 characters per filing on every seat of every session.

04v rejected `message` alone because a script would parse the new id out of text. The MCP server has no script readers, a script reads the id from `filed <id>` with one match, and the command line, where scripts run, never had typed fields for `new`.

**Accepted costs.** A script reading the MCP `new` answer's keys breaks; none is known. The `new` row leaves the MCP answer table in `docs/memory/usage.md`. The CLI `filed` line changes wording, a contract change made on purpose.

**Acceptance.**
1. `agentic-memory new` prints `filed <id>` as its first line, followed by the entry's flags where it has any, and no title, seat, kind, source, time or commit.
2. The MCP `new` answer decodes to an object holding `message` alone, equal to the CLI text.
3. A filing with an attachment, an absorbed entry, an unresolved id, todo items, a near topic and a similar entry names each in the text, as before.
4. `docs/memory/usage.md` and `agentic-helpers:agent-memory` describe the new reply and list no `new` fields.
5. A replayed filing with similar entries answers in fewer bytes than before, measured in the change.
