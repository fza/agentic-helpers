Shell-guard counts the input of a piped shell inside a compound command as replaced only when every redirection onto descriptor 0 is a here-document or here-string, whatever operator or spelling of the number reaches it, in agentic-helpers commit a06dd2d, not yet released, building on 20261031-163018-s-tac-ptl. It replaces 20261031-163956-s-tac-5qx (commit 0fc499c), whose rule still let two cases through: an output operator on descriptor 0 duplicates as an input one does (`{ sh <<< 'echo hi' 0>&3; }`), and the number compared as text missed a padded one (`{ sh 3<&0 <<< 'echo hi' 00<&3; }`, which the shell reads as descriptor 0).

The full rule in `internal/shellwalk`'s `redirectsInput`: an unnumbered redirection reaches descriptor 0 only through an input operator, a here-document or a here-string; a numbered one reaches it when its number parses to 0, or does not parse at all, failing closed. Any such redirection that is not a here-document or here-string (a file, since any name may be a link to `/dev/stdin`, or a duplicate) keeps the shell reported as reading the pipe, and every redirection counts, since zsh's MULTIOS feeds them all. Unnumbered output redirections (`&> log`) never reach descriptor 0 and stay ignored. Accepted cost: `echo x | { sh < script.sh; }` is refused, as `sh < file` at a pipe's end already was. Each check, broken in turn, made its own test fail, and restored, passes; the unparseable-number branch is unreachable by a test, since the parser accepts only digits there. `docs/shell-guard/architecture.md` states the rule.
