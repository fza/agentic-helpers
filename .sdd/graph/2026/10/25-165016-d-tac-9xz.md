The plugin launcher `plugin/hooks/run` never lets a dead fetch hold its lock. The process that takes `.fetch-<version>` writes its pid into `.fetch-<version>/owner` and removes the lock when it exits by any route it can catch: a trap on `EXIT`, `HUP`, `INT` and `TERM`, cleared once the fetch has unpacked or failed. A waiter checks the owner every second while it waits: an owner file naming a pid that no longer runs (`kill -0` fails) means the fetch died uncaught, as under `SIGKILL`, and the waiter removes the lock and fetches itself. A lock with no owner file (one written by an earlier launcher, or caught between `mkdir` and the pid write) keeps the five-minute rule. This ships as a patch release.

Why: the memory MCP server starts through the launcher's `--command` mode, which fetches a missing release first. Claude Code gives an MCP server 30 seconds to connect and then kills it, so a fetch running longer than that dies holding `.fetch-<version>`, with its archive downloaded and nothing unpacked. Every hook and command then waits the full 100 seconds on the lock and falls back to the previous release, and the lock frees only once five minutes old. With v2.2.1 that kept a locale-dependent seat check from reaching the seats it fixes, and Claude Code cached the MCP server's failure for 15 minutes besides.

Rejected: shortening the five-minute rule (a fetch on a slow link can run past any short age and be taken over while alive, fetching twice into one lock); the MCP server starting the newest installed release while the fetch runs (a server of one release beside hooks of another); a lock file held through `flock` (not on macOS by default).

Accepted costs: a waiter now runs `kill -0` once a second; a lock written by an earlier launcher still waits the five minutes; the MCP server's first start can still miss Claude Code's 30-second window when the download itself runs that long, and then fails once, though nothing is left blocked.

Acceptance criteria:

1. A fetch sent `SIGTERM` mid-download leaves no `.fetch-<version>` behind; a test drives the launcher with a slow fake curl and signals it.
2. A lock whose `owner` names a pid that has exited is taken over at once: the launcher fetches and runs the release within seconds, not after 100.
3. A lock with no `owner` file and younger than five minutes is still waited on, and one older is taken over, as `TestAStaleLockIsTakenOver` asserts now.
4. Parallel SessionStart hooks still fetch once.
5. `README.md` describes the owner file and the trap beside the lock.
6. Released as a patch version.
