title: Shell-guard reads script files passed to shells
summary: Decides that shell-guard reads and judges the text of a shell script a command runs, such as `bash x.sh`, `source x.sh`, or a shebang-carrying `./x`, closing the write-then-run bypass where file-based invocations escaped every check. The file goes through the same `internal/shellwalk` syntax-tree walk as `-c` code, interpreter-shebang files fall under existing interpreter rules, and unreadable cases (missing, variable-named, oversized, untraceable) prompt a question instead of refusal. It accepts the cost of a file read per call and judging the script as it stood at check time, with acceptance criteria covering removal detection, grounding-gate visibility, and documentation in `docs/shell-guard/`.
---

Shell-guard reads a shell script a command runs and judges its text as the command's own code: `bash x.sh`, `sh x.sh`, `zsh x.sh`, `source x.sh`, `. x.sh`, and `./x` or `path/x` when the file starts with a shell shebang or none. Today a shell given a file instead of `-c` is never read (`shellCode` in `source/hooks/internal/shellwalk/shellwalk.go` returns nothing without `-c`; a probe showed `bash x.sh` allowed whatever the file held), so an agent can write a script and run it past every check shell-guard makes, removals outside the project included.

**What is read.** The named file, resolved against the command's working directory as far as the walk can follow it (a literal `cd` before it counts), up to 1 MiB. Its text goes through the same syntax-tree walk `internal/shellwalk` runs over `-c` code, so every shell-guard rule applies to it, and the grounding gate (the agentic-helpers hook that makes an agent read the decision graph before an `sdd` or `agentic-capture` write, using the same walk) sees such calls inside it too. A script whose here-document is written by the same command (`cat > x.sh <<EOF ... EOF; bash x.sh`) is judged from that here-document. A file with another interpreter's shebang (`#!/usr/bin/env python3`) falls under shell-guard's existing interpreter rules, which match removal and `mktemp` names in an interpreter's code text (`Inline` in `source/hooks/internal/shellguard/shellguard.go`).

**What cannot be read is asked about, not refused**: a missing file, a path built from a variable or substitution, a path after a `cd` the walk cannot follow, a file over 1 MiB. This is how shell-guard already treats code it cannot read, so `source "$venv/bin/activate"` costs one confirmation rather than a dead end.

**Rejected.** Refusing an unreadable script outright: legitimate calls such as sourcing an activation script by variable would fail every time. Leaving scripts unread: write-then-run would stay an open path past every check.

**Accepted costs.** A file read on every such call. A script changed between the check and the run is judged as it was at the check.

**Acceptance.**
- `bash x.sh`, `source x.sh` and `./x` holding `rm -rf <outside>` get the verdict the line would get on its own; a harmless script passes.
- A missing, variable-named, oversized or untraceable script is asked about.
- A python-shebang file is judged by the interpreter rules.
- The grounding gate sees an `sdd new` inside a sourced script.
- `docs/shell-guard/` and the agent-shell-guard skill describe it.
