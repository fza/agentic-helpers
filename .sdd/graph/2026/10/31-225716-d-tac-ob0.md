Shell-guard follows two more forms of `cd` when it places a script a command runs: a `cd` anywhere in a top-level `&&` chain, and a `cd <dir> || exit` or `cd <dir> || return` statement. Today `plainDirectoryMoves` in `source/hooks/internal/shellwalk/scripts.go` follows only a `cd` that is a statement of its own or opens an `&&` chain of cds, so `cd sub || exit 1; ./build.sh` and `make && cd sub && ./build.sh` lose the directory and ask `cannot read the script build.sh (the directory it runs in is not known)`. The done 20261031-220638-s-tac-7zg names this as left open; this extends the script-reading directive 20261031-211859-d-tac-59g.

**Why these two.** In both, what follows runs only where the `cd` succeeded, so the directory is certain. A `cd` behind another command in an `&&` chain moves the rest of that chain; a statement after the chain loses the place, since it runs whether or not the chain got as far as the `cd`. A `cd <dir> || exit [n]` or `|| return [n]` statement moves every statement after it, since a failed `cd` ends the shell or function there. The `cd` operand stays fixed text naming a directory that exists, as today.

**Rejected.** Following only the `|| exit` form: `make && cd sub && ./x.sh` would keep asking. Keeping today's rule: both common patterns keep costing a confirmation each. Following `cd <dir> || <anything else>` (`|| echo fail`): on failure what follows runs in the old directory, so the place is not certain.

**Accepted costs.** More walk code. A `cd` in a subshell, a function, a branch or followed by `|| echo` still loses the place.

**Acceptance.**
- `cd sub || exit 1; ./x.sh`, `cd sub || return; ./x.sh` and `make && cd sub && ./x.sh` read `sub/x.sh`.
- `make && cd sub && true; ./x.sh` and `cd sub || echo no; ./x.sh` ask `the directory it runs in is not known` for a relative script.
- `docs/shell-guard/usage.md` states the followed forms.
