agentic-helpers scans text bound for its stores and the graph for credentials, through one shared package, `source/hooks/internal/secrets`, and refuses or asks before a credential is kept.

Why: memory entries, attachments, tool scripts and graph entries are shared across sessions, worktrees and seats, readable by sandboxed jobs (20261025-185324-s-tac-k4o), and in the graph's case immutable, so a credential written to one cannot be taken back and reaches every reader. Captured output, a log, a verbose curl, an environment dump, is where credentials leak, and the never-a-credential rule of agentic-memory (20261025-014326-d-tac-mvn) existed only as a skill line.

The scanner:

- The rules are gitleaks' default rule set, pinned: gitleaks v8.30.1, commit `83d9cd684c87d95d656c1458ef04895a7f1cbd8e`, `config/gitleaks.toml` (MIT), 222 rules for provider keys and tokens (AWS, GitHub, Slack, Stripe, private keys, generic API keys and others) and one global allowlist. They are vendored as `rules.json` and embedded with `go:embed`, with gitleaks' license notice beside it.
- `vendor-rules.py` in the package converts the TOML with Python's `tomllib`, so Go carries no TOML dependency; refreshing the rules means moving the pin, rerunning it and committing the result. Its output has the shape the sdd fza fork's converter writes, so the two files are interchangeable: top level `{source: {repository, file, version, commit}, allowlists: [global], rules: [...]}`; a rule `{id, regex?, path?, entropy?, secretGroup?, keywords?, allowlists?}`, keywords lowercased, deduplicated and sorted; an allowlist `{condition?, regexTarget?, regexes?, paths?, stopwords?}`, condition upper-cased, stopwords lowercased. Descriptions and tags are dropped, and the singular and plural allowlist forms both map to one list.
- `secrets.Scan(ctx, text, name) []secrets.Finding` matches with Go's `regexp`, mirroring gitleaks' `detectRule` and `checkFindingAllowed` as the fork does:
  - A rule with keywords runs only when one occurs in the lowercased text, and its patterns compile on first use, so a clean text compiles almost nothing; a rule without keywords always runs.
  - A rule with a `path` applies only when a file name is passed: an attachment's or a tool file's name. Entry text, a state body and a Bash command pass none, so those rules never fire there; a path-only rule fires on the name alone. A global or rule allowlist naming the path skips the whole file when it is OR-conditioned, or AND-conditioned with only paths.
  - The secret is the `secretGroup` group where set, else the first non-empty capture group, else the whole match trimmed of newlines. A match is skipped where the secret's Shannon entropy is at or below the rule's `entropy` floor.
  - Allowlists run global first, then the rule's own. `regexTarget` empty tests the secret, `match` the match, `line` every full line the match spans. An OR list passes on a regex hit or a stopword the lowercased secret contains; an AND list needs every check it carries.
  - Not done, as in the fork: the inline `gitleaks:allow` marker is ignored, since nothing overrides a refusal; encoded segments (base64, hex, percent) are not decoded; `requiredRules` is unused by the file.
  - A finding is the rule id and the 1-based line the match starts on, never the matched text. A refusal names every distinct rule id found on the first finding's line, sorted and comma-separated, and that line.
- The scan runs before any text leaves the machine: agentic-memory and agentic-tools embed what they file through the configured embedding endpoint, so a refused text is never embedded.
- The sdd fza fork scans its own captures with the same pin, shape and semantics, so both refuse the same strings. Its implementation is the source agentic-helpers copies from: commit `26f1aaec` of the fork carries `internal/secrets/rules.json`, `vendor-rules.py`, `LICENSE-gitleaks` and `test/fixtures/secrets/`, which land in `source/hooks/internal/secrets/` and `source/hooks/test/fixtures/secrets/` unchanged. The fixtures are synthetic samples (13 positive, 5 negative, `clean.txt`) and gitleaks' own per-rule samples, `gitleaks/<rule-id>.json` for 220 rules, `{rule, truePositives: [{text} | {path, text}], falsePositives: [...]}`, dumped from gitleaks v8.30.1's config generator (its `utils.Validate` and `ValidateWithPaths`), whose run reproduces `config/gitleaks.toml` byte for byte. A sample with a path is scanned as a file of that name, which covers the path rules. Positions differ only where agentic-helpers sees a different text than sdd does, such as an engine report read as JSON.

Where it runs:

- agentic-memory refuses `new` and `state` when the title or body holds a finding, and `attach` (20261026-222724-d-tac-15x) when the file's raw bytes do: `agentic-memory: <where> looks like a credential (<rule ids>, line <n>); memory never holds one`. Nothing is redacted.
- agentic-tools (20261025-185701-d-tac-e9x) refuses `add` and `update` when the script or its metadata holds one: `agentic-tools: <file> looks like a credential (<rule ids>, line <n>); the library never holds one`.
- The prompt hooks of agentic-memory and agentic-tools scan each user prompt before embedding it for recall (`internal/promptvector`). On a finding no hook embeds the prompt, recall falls back to term matching for that prompt, and the agent hears once: `agentic-memory: this prompt looks like it holds a credential (<rule ids>); it was not sent to the embedding endpoint`. The prompt itself is the user's and is not refused; only its trip to the embedding endpoint, which may be remote, is stopped.
- shell-guard (20261025-235046-d-tac-n48) gains a secrets guard on every Bash command: `agentic-shell-guard: the command holds what looks like a credential (<rule ids>, line <n>); history, logs and files keep it; reference it instead: "$NAME" or a file`. The plugin option `shell_guard_secrets` takes `ask`, `deny` or `off` (default `ask`), as the other guards that can ask take theirs, and its asks follow the permission-mode rule every shell-guard ask follows, decided in its own directive.
- The grounding gate denies a graph write holding one, whichever sdd is installed: a Bash `sdd new` command's text, an `agentic-capture` draft and the files its header attaches, and the report of `mcp__sdd__start_procedure` and `mcp__sdd__next`, read as opaque text. Its PreToolUse matcher gains `mcp__sdd__next`. Wording: `GROUNDING GATE: refused. The capture holds what looks like a credential (<rule ids>, <where>, line <n>); the graph is shared and immutable`.
- At the store migration that brings entry kinds (20261026-215042-d-tac-g5a), agentic-memory scans every entry still holding its body once and lists findings in each owning seat's next brief: `possible credential: <id> <title> (<rule ids>); supersede it --because 'credential'`, since a superseded body drops after 14 days.

Rejected alternatives:

- Importing gitleaks' `detect` package: about fifteen direct dependencies (cobra, viper, lipgloss, archives, a WebAssembly RE2 runtime) in every hook binary, a runtime started in each hook process, felt on every Bash call, and an upstream whose attention has moved to its successor.
- Importing betterleaks, the successor: its v2 is a release candidate, and its dependency tree (git, docker, GitHub and container registry clients) is the heaviest.
- A hand-written rule list: the value is in the provider-specific rules, which a maintained upstream set already carries.
- Redacting findings: a missed variant lands silently next to proof that one was found, and the stored text no longer matches what was captured.
- shell-guard denying by default: a deliberate one-off, a token the user pasted for a login, would be blocked until rewritten; the user decides instead, and `deny` stays a setting. Leaving shell-guard out: a secret run through a command reaches history and files unchecked.
- Scanning graph writes only inside agentic-capture: it is one of three write paths, and a plain `sdd new` or a capture through sdd's engine would pass unscanned. Leaving graph writes to sdd: stock sdd scans nothing, and an entry once written can never be edited. The gate's scan runs on stock sdd and the fork alike (20261026-204842-d-tac-288), and beside the fork's own scan it is a cheap second check on the same rules.

Accepted costs:

- An engine of our own to test, and rules as fresh as the last vendoring run.
- One scan per prompt in the recall hooks, and weaker recall on a prompt holding a credential.
- False positives refuse real text until it is trimmed, and a credential-shaped example in a body has to be rewritten.
- A credential in a shape no rule knows gets through.
- Each refusal's wording is part of its hook's or command's contract, quoted by its skill.

Acceptance criteria:

1. `secrets.Scan` finds every true positive and passes every false positive of `source/hooks/test/fixtures/secrets/gitleaks/*.json`, finds every `positive/` sample, and passes every `negative/` sample and `clean.txt`: the same files the sdd fork tests against, so both tools are held to one set. Breaking the entropy floor, rule allowlists, `secretGroup`, the first-group fallback, the `line` and `match` targets or stopwords each fails this test.
2. A text with no rule keyword compiles no pattern, checked by a test.
3. memory `new`, `state` and `attach`, tools `add` and `update`, each refuse a fixture credential with the wording above; MCP the same. A prompt holding a fixture credential is embedded by neither prompt hook (a fake embedder records no call), recall still answers by terms, and the notice prints once.
4. shell-guard answers a fixture credential in a command with `ask`, `deny` or nothing as `shell_guard_secrets` says.
5. The gate denies `sdd new`, an `agentic-capture` draft and an `mcp__sdd__next` report holding a fixture credential.
6. The migration scan lists a seeded finding in the owning seat's next brief once.
7. `rules.json` carries gitleaks' license notice and the pin in `source`, `vendor-rules.py` reproduces it byte-identically from the pinned upstream file, and it equals the sdd fork's `rules.json` at `26f1aaec` byte for byte.
8. The entropy skip is at or below the floor, the allowlist targets and conditions follow the semantics above, and `gitleaks:allow` overrides nothing, each checked by a test.
9. Every skill quoting a refusal names it, and `docs/` describes the scanner, in the same change.
