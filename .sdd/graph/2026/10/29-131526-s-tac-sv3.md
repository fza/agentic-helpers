`agentic-memory bind <store>` and `agentic-memory merge <a> <b>` let an agent attach its checkout to any store on the machine, or join any two stores, by id, without the user's confirmation reaching the tool; the commands built for 20261028-204914-d-tac-6xf trust the agent to have asked.

**Observed.** An automated security review of agentic-helpers commit 50c9e1c (unreleased) flagged both, confirmed by reading `source/hooks/internal/memory/binding.go`: `bind` passes even while a store question is open and binds to whatever valid store id it is given, whether or not the open question offered it; `merge` with two store ids runs `Resolver.Merge` whatever store the calling checkout resolves to. Store ids are listed in `<data>/index.json` and every `identity.json`, so an agent can read another project's memory and tools by binding to its store, or fold two unrelated projects together. It is a second way into another store beside the silent split-layout join of 20261029-131359-s-tac-5pp: there a committed file opens the path, here the agent's own command does.

**Expected.** The `trust` rule of 20261025-201045-d-tac-vq1, which `bind` replaced, admitted a checkout only from a checkout already listed; binding should be no easier to misuse than that. A bind or merge reaches only the stores the open question for the calling checkout offers, or needs a confirmation the agent cannot give itself.

**Candidate remedies, unsettled:** accept `bind <store>` only for a store the open question for the calling checkout names, and `bind --new` always; accept `merge` only where one side is the calling checkout's own store and the other is offered by its open question; leave the rest to the user through `! agentic-memory ...`, which runs outside the agent's tool calls.
