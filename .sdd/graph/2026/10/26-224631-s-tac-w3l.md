GitHub push protection rejects a push of the shared credential fixtures that the secret-scanning directive (20261026-223236-d-tac-vr7) copies into `source/hooks/test/fixtures/secrets/`: more than 155 of the synthetic samples read as real provider tokens (GitLab, OpenAI, Slack, Stripe, AWS and others). The sdd fza fork, a separate repository (`github.com/fza/sdd`, working on its `fza` branch), had its push of the same files refused that way.

What lets them through: a `.github/secret_scanning.yml` listing `paths-ignore: ["source/hooks/test/fixtures/secrets/**"]`. GitHub's documentation on excluding folders and files from secret scanning (docs.github.com, code-security, customize leak detection) states that paths listed there are excluded from push protection as well as from alerts, and that the file is ignored past 1 MB or past 1,000 entries; it does not say which branch must carry the file.

It follows that a push holding the fixtures passes only once the file is already on the default branch: a later commit in the same push cannot clear a refused commit that itself holds them. The sdd fork landed the file in a commit of its own (`31b32425`, merged into `fza` as `74032928`) and pushed it before the fixtures. This repository, `github.com/fza/agentic-helpers`, a different one from the fork, carries no `.github/secret_scanning.yml` on its default branch `main` today; its `.github/` holds only `workflows/`, so its first push of the fixtures would be refused.
