Shell-guard judges a fish script a command runs the way it judges a file in another interpreter's language: it searches the script's text for removal and `mktemp` names and asks on a match. This covers `fish x.fish` and a file run by its path whose `#!` line names fish. Today neither is read (`docs/shell-guard/architecture.md`, Scripts: the bash parser cannot read fish syntax), so a fish script runs past every check, a write-then-run path the done 20261031-220638-s-tac-7zg lists as left open. This extends the script-reading directive 20261031-211859-d-tac-59g.

**Rule.** The script is read like any other (resolved from the walk's directory, 1 MiB at most; one that cannot be read asks `cannot read the script <name> (<why>)`). Its text goes through the check `python3` code already gets (`Inline` in `source/hooks/internal/shellguard/shellguard.go`), asking `code for fish names a removal` where it names one. A script holding none passes.

**Rejected.** Asking for every fish script: a confirmation for harmless ones too, with no gain over the name check for a removal. Leaving fish unread: the bypass stays open.

**Accepted costs.** A removal word in a comment or a string also asks. A removal's target is not checked against the project, as for other interpreters' code.

**Acceptance.**
- `fish clean.fish` holding `ls; echo done` passes; holding `rm -rf build` it asks.
- `./x` with `#!/usr/bin/env fish` holding `rm` asks; `fish missing.fish` asks `cannot read the script missing.fish (no such file)`.
- `docs/shell-guard/usage.md`, `docs/shell-guard/architecture.md` and the agent-shell-guard skill state it.
