`agentic-memory view --layout '<expr>'` (MCP `view`, keys `layout`, `json`) reads the store through a layout language: colon-chained filters that intersect, then rank and paging, then a required render terminator, with comma-separated sections. The grammar and every word shared with sdd's view layout language (20260717-110000-s-prc-vwg) keep sdd's meaning, so an agent that composes `sdd view` layouts composes these.

Why: memory's reads grow one flag and one MCP key per condition, and several conditions have no flag at all: what was filed for every seat, what was addressed to a seat, which entries need attention. One grammar ends that growth, and the same words already serve sdd's graph.

Vocabulary:

- Shared with sdd: `active` (live entries), `kind(K,...)`, `topic(L)` (component-wise prefix, read through merges), `since("7d"|date)`, `id(...)`, `not(<filter>)`, `rank(heat|by(date))`, `n(N)`, `skip(N)`, `name("...")`, `as-list`, `as-counts`, `as-bodies`, macro `top(N)`.
- Memory's own: `status(live|retired|superseded)`, `seat(s,...)`, `shelf(s,...)`, `for(all|<shelf>,...)`, `from(user|agent|tool)`, `branch(b)`, `linked(<id>)`, `anchored(<path>)`.
- `inbox(<seat>)`: everything addressed to the seat (filed for all, for its shelf, or under a topic its shelf follows), through the one routing function arrival notices use, so the two cannot diverge. `unread` keeps entries filed after the seat's seen mark; a view never moves the mark.
- `returns` (and `returns(anchor|link|until|branch)`): live entries that need attention, each with its reason (anchor drifted or gone, link target closed, superseded or gone, end condition met or inferred, filed on another branch) and the verbs that answer it: anchor drifted → `confirm` where the entry still holds, else `supersede`; anchor gone → `supersede` or `retire`; link target closed or superseded → read the successor, then `supersede` or `retire`; link target gone → `unlink`; end condition met or inferred → `retire`; filed on another branch → none until that branch merges. A reason that cannot be checked shows as `unchecked`, never as absent.

One filter set: every filter is defined once, with its argument parsing, its predicate, and the costly state it needs. `search`'s `--topic`, `--seat`, `--status`, `--all-seats`, the `brief` options and the MCP keys compile to the same filters. `search` keeps `--term` and `--query`, which are search, not filters; `new --for` stays a flag, since it is a write. The brief becomes a fixed named layout: `view --explain brief` prints it, nothing configures it, and its text output stays byte-identical, pinned by golden tests.

Rules:

- A view warms nothing: a listing is not a use (20261026-222129-d-tac-ak9). `show` keeps its warm.
- `--json` answers the entry object and `more.skip` paging of the JSON reads (20261026-214732-d-tac-y5y), keys only ever added, one object per section under the section's name.
- A layout that does not parse, an unknown word or value, or a missing terminator refuses with the token, its position and the nearest valid word; nothing is repaired.
- A layout is caller input only: nothing stored is ever run as one.

Performance, for every read:

- The checkout root and graph config are looked up once per process; today `graphPath` (`links.go:77`) spawns `git rev-parse` per link, 71 of 75 subprocesses of one `show` on a 70-entry store.
- Link and anchor states are computed only for entries a read returns or a filter needs; filters run in one pass, cheap ones first.
- The folded log is cached under the log's segment list, and a call folds only the events appended since.
- Anchor hashes are cached by path, size and modification time.
- `rank` with `n(N)` keeps a bounded heap.
- Any sandboxed job can write the store (20261025-185324-s-tac-k4o): a cache whose key does not match is rebuilt, so a stale or planted cache costs time, never a wrong answer.

Rejected alternatives:

- More flags on `search`: one flag and one MCP key per condition, and the brief keeps its own filtering.
- A JSON object instead of a layout string: schema-checked keys, but a second query language beside sdd's that agents learn separately.
- Importing sdd's parser: it is internal to sdd's module, and memory must not need sdd binary changes; the grammar is small enough to own.
- A configurable brief: its wording is a contract skills quote, and one seat's layout could crowd rules out of another's digest.
- Views stored as entries: stored text becoming runnable queries.
- Per-field indexes: one in-memory pass over ten thousand entries takes milliseconds; the cost is subprocesses and file reads.

Accepted costs:

- A parser and vocabulary to own, kept in step with sdd's shared words.
- Two caches (folded log, anchor hashes) to keep correct.
- The brief re-expressed through the filter set without changing which entries survive its budget.

Acceptance criteria:

1. Every word above parses and filters as stated, table-tested over a fixture store; refusals name token, position and nearest word, CLI and MCP alike.
2. `inbox` and the arrival notice agree on a fixture covering for-all, for-shelf, followed topic and own-shelf exclusion; a view leaves the seen mark and `heat.json` unchanged.
3. `returns` reports each reason, and `unchecked` where the graph cache is cold or a file cannot be read.
4. Golden tests pin `brief`'s text and `search --json` before the filter set replaces their code; both stay byte-identical.
5. One `show` spawns a fixed number of subprocesses whatever the link count, checked by a counting fake; a second read of an unchanged store folds no event.
6. `docs/memory/usage.md`, `architecture.md` and agentic-helpers:agent-memory name the language, the vocabulary and the refusals.
