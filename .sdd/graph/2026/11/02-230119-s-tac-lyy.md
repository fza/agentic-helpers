A checkout moved on a volume without a UUID, such as a tmpfs or a Linux container's own disk, keeps a second entry in its store's identity instead of replacing the old path.

Expected: `admit` in `internal/home/resolve.go` updates an admitted checkout in place when it has the same git common directory or the same volume and inode, "so a moved checkout keeps one entry", which `TestAWorktreeAndAMovedCheckoutKeepTheStore` asserts.

Actual: `fileIdentity` (`internal/home/checkout.go`) records no volume and no inode where `volumeID` finds no UUID; on Linux it looks only under `/dev/disk/by-uuid`, which a container lacks. The moved checkout's pointer still confirms the store, since no admitted path exists on disk any more, but the new path is appended beside the vanished one. `scripts/linux-test` fails on that test for this reason; CI's ubuntu runner has disk UUIDs and passes.

Cost: a store's identity lists paths that no longer exist, one more per move, on such volumes. Nothing resolves wrongly: the pointer keeps the checkout on its store.
