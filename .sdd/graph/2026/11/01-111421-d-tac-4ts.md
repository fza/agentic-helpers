Shell-guard resolves a shell variable whose value the command's or script's own text fixes, and reads a `cd` into the script's own folder as a known directory, before judging removals and move sources. A path so resolved is judged exactly as if written out, for removals and for the sources of `mv` and `git mv`, which shell-guard judges like removals. This answers 20261101-110215-s-tac-e89, where `rm -f "$OPENGREP_HOME/opengrep.download"` and every relative path after `cd "$(dirname "$0")/.."` in fdbox's `scripts/dev-setup.sh` drew asks although both stay inside the project.

**Variables, strict.** A variable resolves at a use only when every assignment shell-guard's parse of the text (the `shellwalk` walk) sees before that use is a top-level statement of the command or script (bare, `export` or `readonly`), not behind another command in an `&&` or `||` chain, and its value is fixed text or fixed text joined with variables that resolve by this same rule. Anything else leaves the variable unresolved and the verdict as today: an assignment in a branch, loop, function, subshell or pipeline; `read`, `unset`, `declare` with options, `local`, a command substitution or arithmetic in the value; a parameter expansion with an operator (`${X:-y}`, `${X%/*}` on a non-`$0` value); a variable never assigned in the text, environment variables included.

**The script's own folder.** In a script the walk reads, `$(dirname "$0")`, `$(dirname "${BASH_SOURCE[0]}")`, `${0%/*}` and `$(cd "$(dirname "$0")" && pwd)`, each optionally followed by fixed text such as `/..`, mean the folder of the script's path as the call ran it, so a top-level `cd` into one is followed like a `cd` to fixed text under the existing `cd` rules. On a command line, `$0` resolves to nothing.

**Why.** These forms carry no information the text does not hold, so asking about them spends the user's attention on removals the guard could judge, and scripts in this style are common.

**Rejected.** Reading values from the hook's environment: the hook's environment is not the shell's at run time. Evaluating the script or a subset of it: running text to judge it is what shell-guard exists to avoid. Resolving the script folder only: fdbox's variable-held paths would keep asking.

**Accepted costs.** A value-tracking pass over each walked command and script, with tests per form; forms outside the lists above keep asking.

**Acceptance.**
- `OPENGREP_TAG=v1.33.1`, `OPENGREP_HOME=.tools/opengrep/$OPENGREP_TAG`, then `rm -f "$OPENGREP_HOME/opengrep.download"` in a script inside the project passes; the same with the assignment inside an `if`, a function or behind `cmd &&` keeps its present verdict.
- A script starting `cd "$(dirname "$0")/.."` judges later relative paths against the script's parent folder; each listed form does likewise.
- A variable assigned from `$(...)`, `read` or never assigned keeps the present verdict, on a command line and in a script.
- `docs/shell-guard/` and the agent-shell-guard skill describe the resolution rules in the same change.
