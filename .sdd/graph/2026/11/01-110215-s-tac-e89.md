Shell-guard asks about removals whose paths a script's own text fully determines.

A variable assigned only fixed text in the same script, and a `cd "$(dirname "$0")/.."` into a directory known from the script's own path, both leave the paths after them unresolvable. Expected, a natural expectation of shell-guard's script reading that no entry states: a removal whose target the script's text alone fixes is judged like the same removal written out, so it passes inside the project instead of drawing an ask.

Observed by the fdbox main seat (2026-11-01), reported by that session and not reproduced here: shell-guard asked on `rm -f "$OPENGREP_HOME/opengrep.download"` in a script where `OPENGREP_TAG=v1.33.1` and `OPENGREP_HOME=.tools/opengrep/$OPENGREP_TAG` are set earlier in the same script, and treated every relative path as unresolvable after the script ran `cd "$(dirname "$0")/.."`.

Candidate remedy raised by the reporting session, unsettled: resolve a variable assigned only fixed text (or fixed text and other such variables) before its use, and read `$(dirname "$0")` as the script's own directory when placing a `cd`. Confidence is medium because the observation is second-hand and the exact script was not read.
