On a colleague's machine, after the migration of 20261028-205958-d-tac-di4 moved agentic-helpers' memory from `~/.claude` into the agent-neutral home, every `agentic-memory` seat claim succeeded while the seat still showed as free; it has not been reproduced on any other machine.

**Actual.** Seen on the colleague's screen by Felix: each claim answered as successful, and the seat listed as free right after. His operating system, how his Claude Code is installed, the release he updated from, and which surface showed the seat free (`who`, the brief, the status line) were not recorded.

**Expected.** A seat a session claims shows as held by that session until it ends or releases it, before and after the move alike.

**Not reproduced** on macOS with isolated homes and checkouts, v2.29.1 updating from v2.15.0 and from releases between v2.2.2 and v2.14.0: claims through the `agentic-memory` command and through the `memory` MCP server, an old-release session still running across the move (its claims refused, as the fence intends), a checkout in sdd's split layout whose `project_dir` names a graph checkout that is absent, and a real Claude Code 2.1.319 (Homebrew) session installing the v2.15.0 plugin, then v2.29.1. In each, `who` and `holder --json` show the seat held, `alive` true. Only a Homebrew install was tried. The native installer, npm and other launch paths were not, though Claude Code is recognised differently under each (`docs/memory/architecture.md`). A claim that finds no Claude Code ancestor still succeeds: it records the immediate parent with no process name, and `seat.Alive` then reads that holder as gone, which would show exactly this symptom.

**Candidate causes, unconfirmed.**
- No ancestor of the claiming call is recognised as Claude Code: the claim then records the immediate parent with no name, and the liveness check, which requires that process to run as `claude`, reads the seat free at once (`internal/seat/seat.go`, `Holder` and `Alive`). An install running Claude Code under another name or path would do this; earlier liveness defects of the same face were 20261025-180318-s-tac-1w8 and 20261029-111908-s-tac-gh0.
- A `memory` MCP server judging claims against stale state, as in the closed gap 20261027-215238-s-tac-q1n; the sandbox's MCP claim showed no such thing.
- Linux, untested: its `/proc` start-time read differs from darwin's kernel read.

A reproduction needs, from the affected machine and a fresh session: `agentic-memory holder <seat> --json` right after a claim, and the process chain above the claiming call.
