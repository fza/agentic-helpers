agentic-memory's `changed:<path>` end drops the could-not-read flag `fileHash` returns, so an unreadable file at check time retires the entry, and a `changed:` end on a directory never fires.

Expected: a `changed:<path>` end fires when the path's content differs from its content at filing, as the end-conditions decision (20261026-215617-d-tac-45q) defines it. Actual, read in the code on `main`: `fileHash` in `internal/memory/anchors.go:91` returns an empty hash and `false` when the path cannot be stat'ed or read, or is not a regular file. Both callers discard that `false`: filing stores the empty hash as the path's hash (`internal/memory/ends.go`, about line 123), and the end check compares the hash it gets against the stored one (`ends.go`, about line 245). A file that is readable at filing and unreadable at a later check (a permission change, a file locked or mid-replace) yields an empty hash that differs from the stored one, and the entry is retired with `end reached: changed:<path>` although nothing about its content is known to have changed. A directory yields an empty hash at filing and at every check, so the end never fires however the directory changes, and filing accepts it without a word.

A fix is being built. Candidates, unsettled: treat a failed read at check time as not reached, and refuse or warn on a `changed:` path that is not a readable regular file at filing.
