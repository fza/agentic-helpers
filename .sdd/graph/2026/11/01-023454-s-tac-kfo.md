Shell-guard's `shell_guard_extra_roots` option is built in agentic-helpers commit e2c72c7 on `main`, not yet released, closing the extra-roots directive (20261101-020134-d-tac-c60).

`pluginconfig.ExtraRoots` parses the `<project>=<root>[;<root>]` entries; `judgeRemoval` gives a path under a matching project's root the inside verdict, so removals, `mv` and `git mv` sources and removals inside scripts all follow it. The project matches on `$CLAUDE_PROJECT_DIR`, so a worktree needs its own entry. The root itself may be removed, since the directive counts a path that is the root as under it. Beyond the directive, a root or project climbing through `..`, written as `/` or `~`, or resolving to either through a link opens nothing, since cleaning `~/../x` would otherwise open `~/x`.

Ignored entries print `agentic-helpers: shell_guard_extra_roots: <entry> ignored; <why>` at session start. A `config.yaml` value prints `config.yaml never sets shell_guard_extra_roots; <value> ignored`, and `config set` refuses it. The option is read from the user's and managed settings only, never from a `--settings` file or the `CLAUDE_PLUGIN_OPTION_SHELL_GUARD_EXTRA_ROOTS` environment.

**Live proof**, headless `claude -p` with the option in an isolated user settings file set to `A=<B>/.tmp`: `rm <B>/.tmp/drafts/from-a.md` from project A ran and deleted the file; the same `rm` from project C was refused `agentic-shell-guard: outside project: <path>` and the file stayed.

Every new guard was broken, caught by its own test and restored byte-identically; a no-`=` check fully masked by the empty-roots check and three unreachable branches were removed. `docs/shell-guard/`, `docs/plugin/usage.md`, both READMEs and the shell-guard skill state it.
