An agentic-memory seat can present work that has already landed as open: nothing ties a todo or trap to the merge or commit that settles it, so the claim brief keeps listing it as live and the agent reports it to the owner as owed. Expected, stated by the owner through the reporting session and recorded nowhere else: a seat always knows when something is already done. The gap closes only where landed work is visible to the seat whenever it reads its todos and traps (at the brief and at the moment work lands), whatever mechanism provides it; fixing one path alone leaves it open.

Observed by the fdbox main seat (store of `format-d-fdbox`, 2026-11-01), reported by that session: its claim brief listed build and brief todos and a trap as live, although every one had been built and merged into its integration branch one to three days earlier (merges such as `autopilot/global-rules` 4e027501cc, `autopilot/adopt-citations` 4d221b765f, `autopilot/e2e-reruns` f2f04d3f48), and the trap's defect was fixed by commit 70b0025a62. The seat's own state slot, in the same brief, said those builds had landed; nothing flagged the contradiction. The only hint was a retired memory link under two of the todos, which does not say done.

How it arose, as reported:
- Filing: the build todos carried no end tied to the work (no `--until merged:<branch>`); some carried only `captured`, some nothing, since the branch name was not known when filed.
- Merging: the seat that merged never ticked or retired them, and nothing at merge time names the live todos and traps a merge settles.
- One todo mixed building and an owed capture; the build ended, the capture stayed, and the brief cannot show half of it done.
- The brief's `retire?` reads only ended links and end conditions, never evidence in git.

Found in the code (`source/hooks/internal/memory/ends.go`, `branch`): `merged:<branch>` ends an entry only while `refs/heads/<branch>` still exists and is an ancestor of its target. A branch deleted after its merge, as worktree branches routinely are, never meets the condition; the entry only draws a `retire?` hint. A `merged:` naming a branch that does not exist yet stays armed already.

Candidate remedies raised by the reporting session, unsettled: (a) at a merge or commit landing, a PostToolUse line naming the seat's live todos and traps whose text, anchors or `--about` paths match the merged branch or changed paths, with the `ack` or `retire` command; (b) a brief line `retire? landed: <sha> <subject>` from commits since filing (subject similarity, branch names, anchors touched), plus a flag where the seat's own state names a todo's work as landed; (c) a filing hint suggesting `merged:<branch>` or items (build, capture) for a build todo with neither.
