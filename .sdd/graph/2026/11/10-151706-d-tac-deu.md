---

Memory's cached graph statuses learn where sdd keeps its local copy of each connected repository by asking sdd: when the cache refreshes through `sdd export --dependencies all`, memory runs `sdd repo path <repo-id>` once per connected repository and stores each answer in `graph-status.json` beside the statuses, and a cached read builds its key from the stored paths without starting a process.

The cache key (`statusKey` in `internal/memory/links.go`) combines the local graph with each connected repository's copy, so a `sdd repo sync` that pulls new statuses into a copy refreshes the flags on cross-repo links (20261026-220938-d-tac-l8w). sdd 0.18.0-alpha.3.fza.43 moved those copies from `<XDG_CACHE_HOME>/sdd/<repo-id>` to `<XDG_DATA_HOME>/sdd/repos/<repo-id>`. The key still reads the old place, finds nothing there (or a stale leftover copy sdd kept for its old index) and never changes, so flags on cross-repo links stay stale until the local graph changes. Asking sdd leaves sdd the only owner of where its copies live.

- Each copy holds its own `.sdd/`; its entries are read through `graphconfig.ResolveAt` as before, which follows the copy's own `graph_dir`.
- The paths sit in `graph-status.json` under `clones`, keyed by repo id.
- Where `sdd repo path` fails, as on an sdd release without it, the stored path is `<XDG_CACHE_HOME>/sdd/<repo-id>`, where those releases keep the copy, so older sdd keeps working (20261027-174929-d-tac-3q0).
- A cache written before this change carries no `clones`; its key no longer matches, so the next read refreshes once.

**Rejected.**
- Following sdd's path rule in Go: no process at all, but a copy of sdd's rule, which already went stale once without notice.
- Asking `sdd repo path` on every cached read: always right, but about 165 ms per connected repository on the read the cache exists to keep fast.

**Accepted costs.** One `sdd repo path` process per connected repository on each refresh. Should sdd move its copies again, cross-repo flags stay stale until the next local graph change refreshes the cache and stores the new paths.

**Acceptance.**
- After a status change lands in a connected repository's copy, the next memory read shows the changed flag, with no local graph change.
- A cached read with no graph changed starts no `sdd` process.
- With `sdd repo path` failing, the key reads `<XDG_CACHE_HOME>/sdd/<repo-id>`.
- A test covers each, with `sdd` faked.
