A `bodies` view and a changed entry both print in full in a live Claude Code session, and commit ef62c33 fixes the defect the live check exposed: an sdd answer that collapsed nothing never recorded what it printed once the agent's shown set held anything. This proves the two paths 20261101-230347-s-tac-fzn left resting on tests.

**Proof.** Runs on `main` with sdd v0.18.0-alpha.2.fza.42, `sessions.token_saving` off in sdd's global config, hooks from `.claude/bin`. The layout `top(2):as-bodies` read twice through `mcp__sdd__view` printed both entries with their bodies both times; `top(2)` then answered both as pointers, so a bodies view marks what it prints. With ef62c33 installed, `id("20261101-230347-s-tac-fzn"):as-list` printed in full, then as a pointer. Commit b63ed90 replaced that entry's summary: the next read printed it in full, the one after as a pointer again.

**Defect.** `Store.Collapse` in `internal/collapse/store.go` took its `before` copy of the set by value, which shares the `Lines` and `Pieces` maps with the set `Answer` writes into. The comparison deciding whether to save always saw no change, so the set stayed on disk as it was unless the answer collapsed something. An entry read after the first view of a set therefore kept printing in full. The fault cost tokens and hid nothing. It sits in the released v2.25.0, and every 2.25.0 session keeps it until a release carries ef62c33.

**Guards.** `TestAnAnswerCollapsingNothingStillGrowsTheSet` covers a new line, a changed line and a new piece. It failed against the unchanged code, and sharing either map again turned its own cases red.

**Also seen, not fixed.** Two `mcp__sdd__view` calls sent in one parallel batch both printed in full on the unfixed build; whether concurrent calls see each other's marks with ef62c33 was not checked.
