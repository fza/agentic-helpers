The landed-commit scan of 20261101-110914-d-tac-pu1 never walks the whole commit graph: it remembers the last commit it examined and starts from there next round, matches an entry only against commits that came after the entry was filed, and runs asynchronously so no hook waits on git. Repositories with huge histories must cost the hooks nothing beyond reading stored results. Matching, storage and delivery stand as that directive and its refinement 20261101-111115-d-tac-js0 set them; these all retire together.

**Scan mark.** Per checkout, the store keeps the sha of the newest commit the last scan examined (`HEAD` at that scan). The next round reads only commits reachable from `HEAD` and not from the mark (`<mark>..HEAD`). Where the mark is no longer an ancestor of `HEAD` (rebase, reset, branch switch), the round falls back to commits reachable from `HEAD` whose committer date is after the mark's, and then moves the mark to `HEAD`.

**Per-entry floor.** A todo, todo item or trap is matched only against commits whose committer date is at or after its filing time (an item's: the time it was added). An entry filed after the mark starts from its own floor, so a newly filed todo never matches older work.

**First round.** Where no mark exists, the round starts at the oldest filing time among the seat's live todos, items and traps on this checkout: commits reachable from `HEAD` with committer date at or after it (`git rev-list --since`), never older. With no live todo, item or trap, the round only sets the mark to `HEAD`.

**Asynchronous.** A hook event that finds a round due starts it as a detached background process and returns at once; the hook only reads mappings earlier rounds stored. One round per checkout runs at a time, held by a lock file; a round finding the lock held exits. A round that dies leaves the mark where the last finished round set it, so the next round repeats its range.

**Efficient.** One `git log` call per round reads sha, committer date, parents, full message and changed paths for the whole range in one stream; nothing is read per commit. A round processes at most a bounded batch of commits (oldest first), moves the mark to the last processed commit, and leaves the rest for the next round. Commit subjects are embedded in one batch call per round, and only for commits newer than the oldest live floor.

**Why.** A full scan on every interval costs time growing with history, and blocking a hook on git would delay every prompt and tool call; an entry matching commits from before it existed would report work it never described.

**Rejected.** Synchronous scans with a time budget: a slow repository still delays the hook up to the budget each time. A date-only window per round (`--since <last scan time>`): commit dates are not monotonic across merges and rebases, so it misses or repeats commits. Scanning every branch: the seat works on `HEAD`'s history, and other branches' merges reach it when merged.

**Accepted costs.** A background process per due round; results lag one round behind the commit that lands; the batch bound means a huge first range takes several rounds.

**Acceptance.**
- A second round with no new commits reads no commits; with new ones, only `<mark>..HEAD`.
- An entry filed after a commit never maps to it.
- A first round with live entries starts at the oldest filing time; without, it only sets the mark.
- After a rebase moving `HEAD` off the mark, the round reads by committer date and recovers.
- The hook returns without waiting on git; two concurrent due events start one round.
- A range larger than the batch completes over several rounds, each moving the mark.
