Under Claude Code installed from npm, whose package now runs the native binary `claude.exe`, every memory seat claim succeeds while the seat reads as free at once, so the next call that needs a seat refuses with `claim a seat first`.

**Actual.** On a colleague's macOS machine (Darwin 27.0.0, Claude Code 2.1.322, agentic-helpers v2.30.0), `memory claim {"name":"diag"}` answered with the seat's brief header, and the `memory brief` call right after refused with `agentic-memory: claim a seat first: memory claim {"name":"<seat>"}`. `agentic-memory holder diag --json` showed the claim with no `alive`, and `agentic-memory who` listed the seat as `free (holder <session> gone, freed)`. `which claude` there is `/opt/homebrew/bin/claude`, which resolves to `/opt/homebrew/lib/node_modules/@anthropic-ai/claude-code/bin/claude.exe`. `ps -o comm` shows that process as `claude`, the name it was started under; the kernel's process name, which memory reads, is the executable's file name. A binary built as `claude.exe` and started through a link named `claude` runs with the kernel name (`ps -o ucomm`) `claude.exe`.

**Expected.** A seat a session claims shows as held by that session until it ends or releases it, whichever way Claude Code is installed.

**Cause, confirmed.** `seat.OwnerAncestor` (`internal/seat/seat.go`) takes a process for Claude Code when it runs as `claude`, as a version-named binary under `claude/versions`, or as `node` running a script of the npm package. `claude.exe` is none of these, and nothing above it is Claude Code, so `seat.Holder` records the claiming call's immediate parent with no process name. `seat.Alive` holds such a claim to a process running as `claude`. For a claim through the `memory` MCP server, whose launcher execs the binary, that parent is Claude Code itself and reads as `claude.exe`; for a claim through the `agentic-memory` command it is the Bash tool's shell. Either way `seat.Alive` judges the holder gone, so `seat.Of` finds no seat for any later call. A claim that finds no Claude Code ancestor still succeeds without a word, so the failure shows only on the next call, under a message that names the wrong remedy. Unobserved, as a candidate: every other caller of the same owner recognition, such as the bind and merge guardrail (`seat.UnderOwner`) and the session-end close (`seat.Owner`), would misjudge such a session too.

This replaces 20261110-190115-s-tac-yyq, whose first candidate cause this confirms and whose others it rules out. The home migration it tied the symptom to plays no part, and its sandbox runs could not show the defect: they used Homebrew's Claude Code, whose binary runs as `claude`. Seat liveness misread the darwin process table once before, for exiting processes (20261029-111908-s-tac-gh0).
