In a checkout whose `.sdd/config.yaml` sets `graph_repo`, memory reads the graph from sdd's own copy of that repository: it asks `sdd repo path <graph_repo>` once, keeps the answer in the store cache as `graph-clone.json` (`graph_repo` and `path`), and asks again only when `graph_repo` changes or the cached folder is gone.

The graph project resolver of 20261026-195422-d-tac-g3w follows `project_dir` to a separate graph checkout. In the `graph_repo` layout sdd reads and writes a copy of its own instead, under `$XDG_DATA_HOME/sdd/repos/<repo-id>`, and the `project_dir` kept beside `graph_repo` for older sdd builds names a checkout sdd no longer updates: in gvb-mika that checkout was 4 hours behind sdd's copy. Memory reading it announces new graph entries late, so `captured` end conditions do not fire, fails to resolve links to new entries, and can take the graph's language from a stale copy. Without `project_dir`, the resolver reads the guard `graph_dir: .sdd/GRAPH-ELSEWHERE.md` as the graph and finds no entries.

- The copy's entries, `repo_id` and `language` are read through `graphconfig.ResolveAt` on the copy, which follows the copy's own `graph_dir`.
- The split-layout link the store mapping joins by (`graphconfig.Link`) keeps following `project_dir` and never names sdd's copy, so no store pointer is written into sdd's clone.
- The `repo_id` a `graph_repo` checkout is matched by in the store mapping of 20261028-204914-d-tac-6xf, and its legacy key, is the `graph_repo` value, read without a process: sdd refuses a copy whose declared `repo_id` differs, and the store has to be found before its cache exists.
- Whether the installed sdd has `sdd repo path` comes from the capability probe of 20261026-204842-d-tac-288 (`internal/sddcaps`), which gains a `repo path` surface: `sdd repo --help` listing `path` among its commands, probed once per binary like `export`, with `surfaces` raised so answers cached before it are probed again. A build without it starts no `sdd repo path` process and memory follows `project_dir` as before (20261027-174929-d-tac-3q0), else reads no graph. A failing `sdd repo path` falls back the same way and caches nothing.
- Connected repositories' copies are found the same way, by asking sdd (20261110-151706-d-tac-deu).

**Rejected.**
- Asking `sdd repo path` in every memory process: no cache, but about 165 ms on every hook call in a `graph_repo` checkout.
- Following sdd's path rule in Go: no process, but a copy of sdd's rule that drifts when sdd moves its copies.

**Accepted costs.** One cache file per store. Should sdd move its copy while the old folder stays, memory reads the old folder until `graph_repo` changes or the folder goes.

**Acceptance.**
- In a `graph_repo` checkout, an entry sdd writes into its copy reaches memory's capture notice with the `project_dir` checkout unchanged.
- A memory process with `graph-clone.json` in place and its folder present starts no `sdd` process.
- Changing `graph_repo`, or removing the cached folder, asks `sdd repo path` again.
- With an sdd lacking `repo path`, memory follows `project_dir` and starts no `sdd repo path` process.
- The `repo_id` the store mapping matches a `graph_repo` checkout by equals the `graph_repo` value.
- A test covers each, with `sdd` faked; `docs/memory/` describes the layout.
