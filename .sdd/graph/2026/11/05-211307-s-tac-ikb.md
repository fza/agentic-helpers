The plugin launcher `plugin/hooks/run` now falls back only to a cached release of the plugin's own major when the release its version names is missing, built in commit 98911a8b on branch `v2` (`fix: launcher fell back to an earlier major's release, whose program printed its usage at SessionEnd`), not yet released.

The defect: under the newest-version-present fallback of the launcher decision (20261023-115644-d-tac-4ni), a session whose release was never fetched ran the newest cached release of any major. A program of another major may know none of the commands this plugin's `hooks.json` calls, so it answered every hook event with its usage line, and SessionEnd's showed in the terminal as the session closed. A release of another major breaks the pairing of the plugin's wiring with the binaries it runs that the plugin delivery (20261023-115501-d-cpt-sd6) rests on, so it no longer stands in: the fallback takes only versions of the plugin's own major. `docs/plugin/architecture.md` states the rule and why.

The subtest `TestAMissingVersionFallsBackToTheNewestPresent/a_version_of_another_major_never_stands_in` fails on its own assertion with the major filter taken out of the launcher, the launcher then running a 1.x release under a 2.x plugin, and passes with the launcher restored byte-identically.
