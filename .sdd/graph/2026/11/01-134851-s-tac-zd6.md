Automatic pruning of stale vector stores shipped on `main` in commits cf74e13 and f077407 (merge 425819e), pushed, not yet released, closing 20261101-131851-d-tac-05m. A daily detached `agentic-helpers prune` deletes a memory or tool-library vector store no binary used for `cache_retention`, judged by `used.json` in the store; agentic-memory's SessionStart and the `memory` and `tools` MCP servers' idle work start it, and after a failed run the next SessionStart prints one line naming the error and `<data>/cache-prune.json`, then never again until a run fails anew.

Every criterion is covered by tests in `internal/vectorseg`, `internal/cacheprune`, `internal/memory`, `internal/pieces` and `internal/pluginconfig`, each guard broken and watched failing on its own assertion. The docs criterion holds: `docs/plugin/usage.md` gains a Cache pruning section, the memory and tools architecture pages and the options table in `docs/memory/usage.md` and `README.md` name `cache_retention`, `used.json` and `<data>/cache-prune.json`. Run live on this machine: every store was used within 90 days, so the run deleted nothing and recorded its status, and a search stamped its store.

Deviations, following the owner's requirement that pruning never be noticeable to a user or an agent, which sdd applies to its own pruning decision (`github.com/networkteam/sdd` entry `20261101-131514-d-cpt-9ci`): one stat per read, a detached run, locks taken without waiting and never the fill lock:

- The run takes only `segments.lock`, never `fill.lock`, which would make a foreground fill skip; a fill that read the store before the hold stamped it, and the stamp is checked again under the hold.
- A read pays one stat: the stamp file is rewritten only once its own modification time is a day old.
- The claim and the warning check read `<data>/cache-prune.json` without a lock and lock only when a run is due or a failure untold; a machine-wide `cache-prune.run.lock`, taken without waiting, keeps one run at a time.
- The MCP servers check after every two quiet minutes, not hourly; on a day the run already started that check is one file read.
- A guard skipping the stamp on a store not yet filled was removed, since the atomic write already refuses a missing folder and no test could fail it.
- The second look at the stamp after the hold guards a race between two processes and is unreachable from a test.

Measured with the benchmarks in `internal/cacheprune` and `internal/vectorseg`: the SessionStart check costs about 78 microseconds on a quiet day, and a store read stays at 38 to 87 microseconds while a run deletes stores beside it against 44 alone, the run holding no lock a read takes.

Open beside it: the tool library's own version pruning still runs inline in SessionStart with a 200 ms lock wait, and a write's room-making waits up to 2 s on another store's lock; neither is part of this directive.
